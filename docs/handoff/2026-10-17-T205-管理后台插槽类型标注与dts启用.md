## 一、背景：T204 留下的取舍

T204 引入按需引入时把 `Components({ dts: false })`，并在 `vite.config.ts` 写明原因：生成
`src/components.d.ts` 后，`vue-tsc` 第一次真正对 Element Plus 的插槽做类型检查，于是 11 个视图里
既有的 `<el-table-column>` 插槽 `#default="{ row }"` 中 `row` 被推断为 `DefaultRow`
（`element-plus/es/components/table/src/table/defaults.d.ts`：`type DefaultRow = Record<PropertyKey, any>`），
传给期望具体类型的函数时报 **79 处错误**，会让 `npm run build`（`vue-tsc -b && vite build`）失败。
T204 为保持 CI 绿先关掉 dts，把修复留作本任务。

## 二、做法

1. **打开 dts**：`Components({ resolvers: [ElementPlusResolver({ importStyle: false })], dts: 'src/components.d.ts' })`。
   生成的声明（83 行）纳入版本管理——`npm run build` 先跑 `vue-tsc -b` 再跑 `vite build`，CI 必须先有这份
   声明，`<el-*>` 与 `v-loading`（`GlobalDirectives.vLoading`）才有类型。`frontend-admin/.gitignore`
   已注明「不要加入忽略」，无两边矛盾。
2. **收窄插槽行类型**：在 78 处报错点把 `row` 收窄为对应业务类型（`f(row as Room)`），类型全部来自各视图
   既有的 `import type { ... } from '@/types'`（`BatchReadingDialog` 为 `@/api/meters`、`prepay` 为 `@/api/prepay`），
   未新增任何 import。
3. **修一处非插槽的类型错误**：`prepay/index.vue` 的 `typeBadgeMap` 原为 `Record<string, string>`，
   其值直接喂给 `<el-tag :type>`，启用 dts 后报 TS2322；改为字面量联合值类型
   `Record<string, 'success' | 'warning' | 'danger' | 'info'>`（键保持字符串索引签名——改成
   `Record<PrepayTransactionType, …>` 会让 `row.type`（`any`）索引触发 TS7053）。
4. **未改**：模板结构、事件绑定、脚本逻辑、`element-plus/dist/index.css` 全量样式链路（T204 的刻意选择）一律未动。

## 四、为什么没有用「插槽标注」写法

任务书原定 `<template #default="{ row }: { row: Room }">`。实测在本仓库 tsconfig（`@vue/tsconfig`
的 `strict: true`）下**不成立**，四种写法逐一验证：

| 写法 | 结果 |
| --- | --- |
| `#default="{ row }: { row: Building }"` | ❌ `TS2345: Argument of type '(_: { row: Building; }) => any' is not assignable to parameter of type '(props: { row: DefaultRow; column: TableColumnCtx<DefaultRow>; $index: number; }) => any'`（原有内层错误也仍在） |
| `#default="{ row }: { row: Building; column: any; $index: any }"` | ❌ 同上——slot 函数参数受 `strictFunctionTypes` **逆变**校验，注解类型必须是 Element Plus 声明类型的**超类型**，收窄必然失败 |
| `#default="{ row }: any"` | ✅ 能编译，但 `row` 退化为 `any`，等于放弃检查（只是消音，不可取） |
| 注解 + `tsconfig` 关 `strictFunctionTypes` | ✅ 能编译，但为模板写法全局放宽函数类型校验（本仓库刚做完 T190 类型安全治理），不可接受 |
| 注解 + `vueCompilerOptions.strictTemplates: true` | ❌ 无效，且在 `buildings` 单文件上额外暴露 2 处无关错误（`:total` 的 `number \| undefined`、`:disabled` 的联合类型） |

结论：在这种「组件声明了精确 slot props、项目又开了 `strictFunctionTypes`」的组合下，插槽注解无法收窄。
改为**调用点收窄**：调用点的收益与注解等价（传给业务函数的 `row` 拿到真实类型），且不放宽任何编译配置。
