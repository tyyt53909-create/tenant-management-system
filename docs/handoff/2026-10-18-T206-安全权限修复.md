## 一、档案下载越权（IDOR）

- **缺陷**：`GET /api/files/:key?expiresIn=<n>` 在 `assertCanRead(key, user)` **之前** 就 `return res.json(await signUrl(...))`。T159 补的归属校验只挡住了「不带 expiresIn」的那条分支；带 `?expiresIn=` 时任何已登入的 TENANT/CLEANER 只要拿到他人 key，就能换出一个签名 URL —— `STORAGE_DRIVER=s3`（生产用阿里云 OSS）下那是可直接下载他人身分证/合约扫描的真预签名位址，效期还由请求方自订。
- **修复**：把 `await this.filesService.assertCanRead(key, user)` 提到方法最前面，两条分支共用。
- **测试**：新增 `backend/src/modules/files/files.controller.spec.ts`（5 例：非本人+expiresIn 拒绝且不签名、本人放行、ADMIN 放行、非法 expiresIn 回退 3600、非本人不带 expiresIn 拒绝且不读档）。
- **回归验证**：把控制器暂时还原成修复前的顺序后跑该 spec → **2 例失败**（正是越权那两条），还原修复后 5 例全绿。归属判定本身在 `files.service.spec.ts` 已有完整覆盖，本次补的是控制器接线。

## 二、OTP 路由失去每 IP 限流

- **缺陷**：`OtpEmailThrottle()` 原先给 `default` 限流器挂 `getTracker: otpEmailTracker`。@nestjs/throttler 6.7.1 的 guard 是这样的（`throttler.guard.js:94`）：

  ```js
  const getTracker = routeOrClassGetTracker || namedThrottler.getTracker || this.commonOptions.getTracker;
  ```

  每条路由对每个命名限流器只保留**一个** tracker，所以路由级的 getTracker 直接顶掉了 `commonOptions` 的 IP tracker。结果：`POST /api/auth/send-email-code` 只剩「每邮箱 5 封/小时」，未登入者换一个邮箱就是一个新桶 —— 可拿本站信誉为不限数量的收件人寄验证码信（寄信轰炸、烧 SMTP 额度）。
- **修复**：把邮箱计数拆到**独立的命名限流器** `otpEmail`（tracker 由模块配置提供），路由上的装饰器只收紧它的次数，`default` 保持按 IP：
  - `throttle.config.ts`：新增 `OTP_EMAIL_THROTTLER_NAME`、`otpIp`（默认 30/小时/IP，可用 `THROTTLE_OTP_IP_LIMIT` 覆盖）、`createThrottleModuleOptions` 增加第二个 throttler；
  - `throttle.decorators.ts`：`OtpEmailThrottle()` 同时设置 `default`（每 IP）与 `otpEmail`（每邮箱），**不再**覆盖 tracker。
- **测试**：`throttle.http.spec.ts` 新增「换邮箱不能绕每 IP 上限」；原「同一邮箱第 6 次 429」改为每次换来源 IP，使两层各自独立受测；元数据测试改为断言「路由收紧 `otpEmail` 且**没有**给 `default` 挂 tracker」。
- **注意（API 表面变化）**：具名限流器被挡时，@nestjs/throttler 会把标头写成 `Retry-After-otpEmail` 而非 `Retry-After`（`getThrottlerSuffix`）。两个前端都没有读这个标头（已 grep 确认为 0 处），故无客户端影响；已在测试注释里写明。

## 三、Google 模拟登入后门

- **缺陷**：mock 分支只以 `NODE_ENV !== 'production'` 把关，且触发器之一是「**没有**配置 `GOOGLE_CLIENT_ID`」—— 部署若漏设 NODE_ENV（staging/typo/未设）且没配 Client ID，`POST /api/auth/google {"idToken":"mock-google-token:admin@example.com"}` 就能冒充既有 ADMIN 帐号（federated auth 以 email 命中使用者）。与隔壁 OTP 万能码「`NODE_ENV=development` **且** `OTP_DEV_BYPASS=true`」的双开关设计不对称。
- **修复**：
  1. 新增显式开关：`GoogleAuthService.isMockEnabled()` = `GOOGLE_AUTH_MOCK === 'true' && NODE_ENV !== 'production'`；
  2. 看起来像 mock token 但通道未启用 → 明确 `UnauthorizedException('模拟 Google 登录通道未启用…')`，不再静默；
  3. 未配 `GOOGLE_CLIENT_ID` 且模拟关闭 → `ServiceUnavailableException('服务端未配置 GOOGLE_CLIENT_ID…')`；
  4. `GET /auth/google/client-id` 回应新增 `mockEnabled`，前端据此显示/隐藏「模拟 Google 登录」开发者通道（原先用「没有 clientId」推断，会在生产把用户导向一个必然失败的入口）；
  5. `.env.example` 与 `docs/12 §1.1` 登记 `GOOGLE_AUTH_MOCK`（保持 doc-check 的变量清单一致性门禁为绿）。
- **测试**：`google-auth.service.spec.ts` 新增 3 例（未开开关时 mock token 被拒、生产环境即使开开关也拒、未配 Client ID 时给明确错误），既有 mock 解析测试补上开关与 NODE_ENV。
- **本地开发注意**：本机 `backend/.env` 需自行加 `GOOGLE_AUTH_MOCK=true` 才能继续用模拟 Google 登入；`.env.example` 默认是 `false`。
