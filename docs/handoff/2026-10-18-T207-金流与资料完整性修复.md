## 一、退租结算凭单：扣款分类用了不存在的枚举值

- **缺陷**：`checkout.service.ts` 的凭单汇总把扣款写成
  `['DAMAGE_COMPENSATION','CLEANING_FEE','OVERDUE_FEE','OTHER_DEDUCTION']` —— 这四个值在 Prisma 的
  `CheckoutItemType`（`RENT_REFUND/DEPOSIT_REFUND/DEPOSIT_DEDUCTION/UTILITY_REFUND/OTHER_FEE/OTHER_REFUND`）
  里**都不存在**，而 DTO 用 `@IsEnum` 只放行真值，所以生产数据永远匹配不到 → `totalDeduction` 恒为 0、
  `netRefund` 在 `totalRefund` 为空时按「零扣款」重算 → 实退金额被高估；退款侧又漏了 `UTILITY_REFUND`。
  前端 `SettlementVoucherModal.vue` 用同一份错清单，把押金扣除显示成 `+¥` 并露出原始枚举名。
- **为什么测试没抓到**：`checkout.service.spec.ts` 的凭单测试用的也正是 `CLEANING_FEE`（数据库里不可能出现），
  恰好命中服务里同样错误的清单，于是「断言通过」。
- **修复**：
  - 新增 `backend/src/modules/checkout/checkout-item-types.ts`，把两组分类声明为
    **`readonly CheckoutItemType[]`** —— 写错类别名会直接编译失败（已实测：旧清单报 4 个 TS2322）；
  - 服务与前端都改用真实枚举；前端补 `UTILITY_REFUND` 等标签与正确的正负号判定；
  - 新增 `checkout-item-types.spec.ts` 断言两组**恰好划分**枚举（不重不漏）；
  - 修正被污染的凭单测试（改用真实类别 `OTHER_FEE`），并新增「`totalRefund` 为空时按明细重算、扣款与水电退款都计入」一例。
- **验证**：把分类换回旧清单（绕过类型）后，3 个分组测试全红；还原后 3 绿。

## 二、合同状态机可被 PATCH 绕过

- **缺陷**：`PATCH /api/contracts/:id` 直接 `if (dto.status) updateData.status = dto.status`，不校验流转、不碰房间。
  `TERMINATED` 可复活为 `ACTIVE`（docs/04 §2.4 明定终态不可逆），房间却仍是 `VACANT+CLEAN` → 继续出现在公开看房可租列表，
  同一房间可再出租；月账单只认 `ACTIVE`，会对已退租租客重新出账。`DRAFT` 也能一步跳到 `RENEWED`/`EXPIRED`。
- **修复**：新增 `backend/src/modules/contracts/contract-transitions.ts`（docs/04 §2.3 的可执行版本）：
  - `CONTRACT_TRANSITIONS`：`DRAFT→{ACTIVE}`、`ACTIVE→{EXPIRED,TERMINATED,RENEWED}`、`EXPIRED→{RENEWED}`、终态无出边；
  - `roomUpdateForContractTransition()`：`DRAFT→ACTIVE` → 房间 `RESERVED→OCCUPIED`；`ACTIVE→TERMINATED` → `OCCUPIED→VACANT+PENDING_CLEAN`；
    **房态前置条件不满足时返回 null（不强改房态）**，与既有定时任务语义一致；
  - `update()` 校验非法流转抛 409（带 docs 出处），把状态写入与房间随动放进同一事务；
  - **定时任务的 `autoTransitionContracts` 改用同一份规则**（原先内联判断 `room.status === 'RESERVED'`），避免两处漂移。
- **范围说明**：`ACTIVE→TERMINATED` 只做房间随动，**不自动创建退租记录**（那仍是退租流程的职责）；
  §2.3 的「可操作角色」未按角色细分（控制器层已有 `@Roles`）。

## 三、新建合同缺两条校验

- **缺陷**：`create()` 不检查「同房源是否已有未结束合同」，也不校验 `endDate > startDate`（而 `renew()` 一直有）。
  两份 DRAFT 会被定时任务一起置为 ACTIVE，月账单幂等键是 `contractId+period`（**不含 roomId**）→ 同一房间同一月两笔租金账单；
  反向日期会「已生效却零账单」。
- **修复**：`create()` 增加日期顺序校验（400）与「同房源已有 DRAFT/ACTIVE 合同」检查（409）。
- **未含**：数据库级的部分唯一索引（`roomId where status in ('DRAFT','ACTIVE')`）才是并发下的最终保证，
  需迁移且要先把既有重复数据清干净，属独立任务（见 §5）。

## 四、报修工单状态机可被 PATCH 绕过

- **缺陷**：`update()` 直接写任意 status：`COMPLETED` 可退回 `SUBMITTED` 并重新进看板统计（§4.4 明定终态不可逆）；
  可 `{status:'ASSIGNED'}` 跳过「受理」且不填 `assignedTo`；`{resolution:'x'}` 会在状态仍为 `SUBMITTED` 时就写 `resolvedAt`。
- **修复**：新增 `backend/src/modules/maintenance/maintenance-transitions.ts`（§4.3）；`update()` 校验流转（409）、
  派单必须带 `assignedTo`（400）、`resolvedAt` 只在「确认完成」时写（`resolution` 仍可随时补填）。

## 五、两处金额/口径小缺陷

- **预付账户阈值**：`lowBalanceThreshold: dto.lowBalanceThreshold || 10000` 会把显式传的 `0`（语义：不提醒）改成 10000 分；
  同文件 `update()` 用 `!== undefined` 才是对的。已改为 `??`，并新增「显式 0 保留 0」测试。
- **统计出账额与出租率**：
  - `rentBilled/utilityBilled` 原先不排除 `CANCELLED` 账单 → 出账额虚高、`collectionRate` 分母被灌水，且与
    `dashboard/management-summary` 明确使用 `status:{not:'CANCELLED'}` 的口径矛盾。已在查询层排除。
  - 出租率原先用「当下的 ACTIVE 合同」套到任意历史区间（查 1 月报表返回今天的占用数）。现改为按**统计区间末端**计算：
    `startDate <= asOf && endDate >= asOf`，状态取 `ACTIVE/EXPIRED/RENEWED`；**区间末端若在未来（本月/本季报表）以当前时刻为准**，
    避免出现「月末前瞻空档」。语义仍与档头注释一致（区间末占用房间数）。

## 七、遗留与建议

1. **同房源唯一性**：需数据库级部分唯一索引（`CREATE UNIQUE INDEX ... ON contracts(room_id) WHERE status IN ('DRAFT','ACTIVE')`）。
   属 schema 变更 + 迁移，须先确认线上无重复数据；应用层校验已就位。
2. **合同 §2.3「可操作角色」**：目前只做流转校验，未按角色细分（如 `ACTIVE→TERMINATED` 仅管理者）。
   控制器层 `@Roles` 仍生效，但若要让租客也能「取消自己的报修」之类，需要引入按流转的角色矩阵。
3. **退租记录自动创建**：`ACTIVE→TERMINATED` 目前不自动建退租记录（见 §2 范围说明）；若产品要求，可在退租流程里补一个「由合同终止触发」的入口。
4. **月账单幂等键**：`RENT:{contractId}:{period}` 不含 roomId，所以「同房源唯一性」是这条幂等键成立的前提，两者应一起看。
