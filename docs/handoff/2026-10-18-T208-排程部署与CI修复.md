## 一、逾期天数与提醒：业务日 vs UTC 的错位

- **缺陷**：`checkOverdueBills` 用 `startOfTodayUtc()`（**业务日**上海零点，UTC 表示）判断—「`dueDate < today`」——挑出昨天到期的账单并把状态改成 `OVERDUE`；但紧接着 `LateFeeUtil.overdueDays(dueDate)` 内部用的是 `new Date()` 的 **UTC 日历日**。daily cron 是 `0 0 1 * * *` Asia/Shanghai（= 前一日 17:00Z），此刻「业务日」已是 D 而 UTC 日期还是 D-1 → 对 D-1 到期的账单算出 **0 天**：
  - `addLateFee` 抛 `BadRequestException('账单尚未逾期')` → 被 catch 成一条 warning，`suggested` 永远是 0；
  - 而该账单已在同一轮被改成 `OVERDUE`，第二天查询条件 `status in (PENDING,PARTIAL)` 不再包含它 → **这张账单的滞纳金建议永远不会产生**（手动重跑也救不回）；
  - 通知文案变成「您有账单逾期 0 天」；`[1,3,7]` 提醒节点整体延后一天。
  - 测试掩盖原因：`FIXED_NOW = 2026-10-13T04:00:00Z`（= 上海 12:00）时两种算法结果相同。
- **修复**：
  - `LateFeeUtil.overdueDays(dueDate, now = new Date())` 保持纯函数，改由调用方传入正确基准；
  - `BillLateFeeService.addLateFee(billId, dto, operator, referenceDate?)` 新增可选基准参数（API 手动加滞纳金时仍用真实 now）；
  - `SchedulerDailyJobsService` 的两处调用与 `addLateFee` 调用统一传 `today`（业务日零点）。
- **回归验证**：新增「凌晨 01:00（上海）执行时仍按业务日算逾期天数并成功给出滞纳金建议」——把修复还原后该测试**失败**（逾期 0 天、不给建议），还原修复后通过。

## 二、逾期提醒被自己的去重键吞掉；同日去重窗口失效

- **缺陷**：
  1. `[1,3,7]` 三个节点的 title 都是「账单逾期提醒」，而 dedupKey 是 `BILL_REMINDER:{userId}:{billId}:{title}` —— **不含节点维度**，于是第 3、7 天写入时 dedupKey 完全相同，`InAppChannel` 的 `create` 触发 P2002 后回传已有通知且不报错 → 第 3 天与第 7 天提醒永远不会出现；
  2. 「同一收件人当天只发一次」用 `createdAt >= startOfTodayUtc()` 过滤，而业务日零点在凌晨 01:00 执行时**落在未来**，条件永远不成立；
  3. `notify()` 吞掉异常后调用方仍 `sent++`，`summary` 虚报发送数。
- **修复**：去重键加入节点（`overdue-d1/d3/d7`、`due-in-3/due-in-0`）；同日窗口改用新增的 `startOfUtcDay()`（当前 UTC 自然日零点，与 `createdAt` 同一时间基准）；`notify()` 改为返回 `boolean`，调用方据此计数。月账单服务同样修正了通知计数。
- **测试**：新增 3 例（节点维度去重键、凌晨执行时窗口取 UTC 自然日零点、通知失败不计入 sent）。

## 三、月账单生成：一个合同失败就中止整批，且仍记成功

- **缺陷**：整个 `for` 迴圈包在**同一个** try/catch 里，第 N 个合同出错就跳出迴圈，其后所有 ACTIVE 月付合同本期完全没有账单；异常只被 push 进 `summary.errors` 后正常返回 → `JobRunner` 记 `SUCCESS`，运维在 `job_runs` 上看不到任何异常。月账单每月 1 日才跑，恢复只能靠人工重跑。
- **修复**：把 try/catch 收进**单个合同**的循环体内（其余合同继续出账），查询合同的失败仍视为整体失败；循环结束后若 `summary.errors.length > 0` 则 `throw`，让 `job_runs` 记为 `FAILED` 并留下 `errorSummary`。
- **测试**：新增「单个合同失败不中止其余合同，且任务以失败收尾」。

## 四、咨询锁的 5 秒事务超时（连带修复，不在审查前 15 条内）

- **缺陷**：`PrismaAdvisoryJobLock` 用 `pg_try_advisory_xact_lock` 抢锁，锁跟随**事务**生命周期；而 Prisma 交互式事务默认 `timeout: 5000ms`，任务跑超过 5 秒就会回滚 → 锁提前释放（任务本体走其他连接仍在跑），第二个实例即可并行执行同一任务；同时这次运行被记成 FAILED。
- **修复**：显式给该事务 `timeout: 30 分钟`、`maxWait: 10 秒`（并写明为何必须大于任务时长）。

## 五、生产镜像：错架构的 Prisma 引擎

- **现象**：本机 `tenant-prod-backend-1` 一直 **crash loop**，日志是
  `Prisma Client could not locate the Query Engine ... libquery_engine-linux-musl-arm64-openssl-3.0.x.so.node`。
  实测该镜像：`linux/arm64`、容器内 `node arch=arm64`，但 `node_modules/@prisma/engines` 里只有 **x64** 的
  `libquery_engine-linux-musl-openssl-3.0.x.so.node`，`.prisma/client` 里则没有任何 `.so.node`
  → 引擎版本与运行架构不匹配，启动即崩（nginx 前端的 `/api` 全部不可用）。
- **查明**：当前 `backend/Dockerfile` 的 `uname -m` 分支逻辑其实是**对的** —— 实测 `node:20-alpine` 里 `uname -m` = `aarch64`，重新构建后产出的是
  `libquery_engine-linux-musl-arm64-openssl-3.0.x.so.node` ✅，容器内实例化 `PrismaClient` 再查询已经不再是「引擎缺失」而是连接错误 ✅。
  也就是说：**崩掉的那颗镜像是更早版本 Dockerfile 构建的**（T198 当前的架构分支是后来才加的），仓库里的 Dockerfile 本身没问题。
- **修复（防回归）**：在 builder 阶段 prune 之后加了构建期断言 —— 必须能找到查询引擎，且引擎名字要与 `uname -m` 一致（arm64 镜像不得是 x64 引擎，反之亦然），否则**构建失败**。这样同类问题会在 CI/构建期暴露，而不是等到部署启动才崩。
- **未验证**：amd64 分支（生产服务器）没有在本地模拟构建验证，逻辑上与 arm64 分支对称。

## 六、CI 的 ENCRYPTION_KEY 不合法（30 字节）

- **缺陷**：`backend-ci.yml`、`backend-e2e.yml`、`admin-ui.yml` 都把 `ENCRYPTION_KEY` 设成 `test-encryption-key-32-bytes!!`（**30** 字节）。实测 `resolveFieldKey()` 会抛「必须是 32 字节」→ 任何走到证件号加解密（`hashIdNumber`/`decrypt`）的测试或 e2e 流程都会失败；目前全绿只是因为没有任何流程碰到它 —— 一颗定时炸弹。
- **修复**：三个 workflow 统一改为 `ci-test-encryption-key-32-bytes!`（**32** 字节，已实测被 `resolveFieldKey` 接受）。

## 七、refresh 令牌轮换的并发与重放

- **缺陷**：轮换是「`get` → 判断 `status === 'rotated'` → 签发新令牌 → `save` 新 → `save` 旧为 rotated」，三步之间没有原子性（内存与 Redis 两种 store 都一样）。两个并发刷新会**都通过判断**，重放检测（本类别的防护目的）形同虚设；反过来，管理后台多标签页、小程序首屏并发 401 都会真的并发刷新 —— 第二个请求带的是刚被轮换的 jti，于是触发 `revokeUser`，把**包含刚发出的新令牌在内**的整个会话家族撤销，用户被强制登出。
- **修复**：
  - `RefreshSessionStore` 新增 `rotate(jti, replacedBy): Promise<boolean>`（compare-and-set）：内存实现直接用 Map 同步读改写（JS 单线程天然原子）；Redis 实现用 `SET rotatedMarkerKey NX PX` 抢标记键（ioredis 命中已存在键返回 null），抢到才算赢家，并给旧会话补写 `rotatedAt`；
  - `JwtAuthService.rotateRefreshToken`：先签发（失败即丢弃，不用标记会话），再原子 `rotate`；输家若在 **30 秒宽限窗口**内（`ROTATION_RACE_GRACE_MS`）返回 401「刷新令牌正在轮换中，请稍后重试」且**不**撤销会话家族；超出窗口才按重放处理（撤销全家 + 401「已重复使用」）。
  - `RedisCommandClient.set` 增加可选 `condition?: 'NX'`（ioredis 原生支持，原有调用不受影响）。
- **客户端后续行为（已确认无需改动）**：refresh token 存在**共享 Cookie** 里，赢家那次响应已经把新 Cookie 写回浏览器；输家标签页被 401 后会走登录页 → 重新加载时 `restoreSession()` 用的是新 Cookie → 自动恢复，不需要用户重新输入密码。
- **权衡**：宽限窗口内不判定重放，意味着「令牌刚被轮换后的 30 秒内重放」不会触发全家撤销 —— 用这一点点检测强度换取「并发刷新不再把用户踢下线」。阈值是模块常量，可按需收紧。

## 十、补修：并发刷新的宽限窗口判定（审查复验，2026-10-18）

§7 的 refresh 原子轮换**没有真正生效**：输家用的 `rotatedAt` 取自轮换**之前**读到的
`current` 快照，而真实并发下两个请求都在任何人轮换之前读完会话，快照里根本没有
`rotatedAt` → `withinGrace` 恒为 false → 输家落进「重放」分支并 `revokeUser`，
把赢家刚签发的新会话一起撤销。原测试只覆盖「第二个请求在第一个完成之后才进来」的
顺序情形，因此没暴露。

反证（不打桩，`Promise.allSettled` 同时调两次 `rotateRefreshToken`，200 轮）：

- 修复前：**200/200** 判为重放并撤销家族，赢家新令牌 200/200 失效（用户被强制登出）；
- 修复后：200/200 识别为竞态，0 次撤销。

改动：

- `RefreshSessionStore.rotate` 返回 `{ rotated, rotatedAt }`，输家也能拿到赢家的轮换时刻；
- Redis 实现的「已轮换」标记键**值改为轮换时刻**（原先存 `replacedBy`，无人读取）；
  标记先于会话本体写入，故中间态下输家仍能拿到正确时刻；
- `rotateRefreshToken` 的宽限判定改用 `rotate` 的返回值，不再读旧快照；
- 新增回归测试：`jwt.service.spec.ts`「真并发（两个请求都在轮换前读完会话）」、
  `refresh-session.store.spec.ts` 标记中间态用例。

验证：后端 `npm test` 821 例全绿（819 → +2）、`lint` exit 0、`nest build` 与
`openapi:check` 121 条路由一致。

仍待处理（本轮未做，属客户端行为）：宽限窗口内客户端拿到的是 401「正在轮换中」，
管理后台 `request.ts` 在刷新失败时会 `expireSession()`，因此**输的标签页仍会显示登出**
（会话本身已保全，刷新页面即恢复）。若要端到端消除，需在前端对「正在轮换中」重试一次
（此时新 cookie 通常已由赢家写入）。

## 十一、补修：客户端对「并发轮换」的处理（2026-10-18）

§7 与 §十 修好的是服务端不再撤销会话家族，但客户端拿到 401 后仍然会直接登出，
于是「多标签页同时刷新」在用户侧看仍然是掉线。两端各补一处：

- **管理后台** `src/utils/request.ts`：刷新失败时若错误是「正在轮换中」，等 300ms 后用
  新的 refresh cookie 重试一次（赢家已把新 cookie 写进浏览器）；其它失败照旧直接登出。
  新增两条测试：竞态重试成功且不 expireSession、cookie 失效不重试。
- **小程序** `utils/request.js`：原先并发 401 会各发一次刷新，而且刷新失败一律清空存储
  —— 会把赢家刚写入的新令牌一起清掉。现在同一运行时的并发刷新共用同一个 promise（单飞），
  跨运行时的竞态（H5 多标签）则改用共享存储里的新令牌重试一次；两者都不再清会话。
  新增两条测试：并发 401 只刷新一次各自重试、跨运行时竞态重试成功且不清存储。
