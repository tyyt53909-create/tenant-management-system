### 2. 权限控制实现

```typescript
// 装饰器定义
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

// 守卫实现
@Injectable()
export class RolesGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    
    if (!requiredRoles) return true; // 没有角色要求
    
    const user = request.user;
    return requiredRoles.includes(user.role);
  }
}

// 使用方式
@Post()
@UseGuards(RolesGuard)
@Roles('ADMIN')
create(@Body() dto: CreateRoomDto) {
  return this.roomsService.create(dto);
}
```

**优点**：
- 声明式权限控制
- 易于维护和扩展
- 自动拦截未授权访问

### 4. 业务逻辑

#### 房号唯一性检查

```typescript
// 唯一性约束：buildingId + floor + roomNumber
const existingRoom = await this.prisma.room.findFirst({
  where: {
    buildingId: dto.buildingId,
    floor: dto.floor,
    roomNumber: dto.roomNumber,
  },
});

if (existingRoom) {
  throw new ConflictException('该楼栋下该楼层的房号已存在');
}
```

**注意**：
- Prisma Schema 中定义了 `@@unique([buildingId, floor, roomNumber])`
- 创建时检查
- 更新时排除自身

#### 楼栋验证

```typescript
const building = await this.prisma.building.findUnique({
  where: { id: dto.buildingId },
});

if (!building) {
  throw new BadRequestException('楼栋不存在');
}
```

#### 硬删除 vs 软删除

**当前实现**：硬删除
```typescript
await this.prisma.room.delete({ where: { id } });
```

**原因**：Prisma Schema 中 Room 表没有 `isDeleted` 字段

**生产环境建议**：
- 检查是否有关联数据（合同、报修等）
- 如果有关联，拒绝删除或使用级联删除
- 考虑添加 `isDeleted` 字段实现软删除

### 5. 分页查询

```typescript
const skip = (page - 1) * limit;

const [data, total] = await Promise.all([
  this.prisma.room.findMany({

return {
  data,
  meta: {
    page,
    limit,
    total,
    totalPages: Math.ceil(total / limit),

```

## 与 Prisma Schema 的差异

### Schema 定义 vs 实现

| 字段 | Schema | 实现 | 说明 |
|------|--------|------|------|
| monthlyRent | ❌ 不存在 | ❌ 未实现 | 租金在 Contract 表中 |
| deposit | ❌ 不存在 | ❌ 未实现 | 押金在 Contract 表中 |
| isDeleted | ❌ 不存在 | ❌ 硬删除 | 未来可添加软删除 |
| bedrooms | ❌ 不存在 | ❌ 未实现 | 由 roomType 决定 |
| bathrooms | ❌ 不存在 | ❌ 未实现 | 由 roomType 决定 |
| facilities | ✅ JSON | ✅ JSON | 设施信息（灵活） |
| version | ✅ 乐观锁 | ❌ 未使用 | 并发控制（第二阶段） |

### 设计理由

**为什么租金不在 Room 表？**
- 租金可能变化（涨价、优惠）
- 每个合同的租金可能不同
- 历史租金需要保留

**为什么用 facilities JSON？**
- 灵活性高
- 不需要固定的字段
- 前端可以动态渲染

**为什么用 roomType 而不是 bedrooms？**
- 更符合中国租房习惯
- 包含更多信息（单间、开间）
- 前端易于展示
