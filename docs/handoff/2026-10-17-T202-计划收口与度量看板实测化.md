## 一、发现的缺陷（均已修复）

### 1. 后端生产构建失败（P0，CI 阻断）

- `backend/src/common/utils/scoped-where.ts:16` 报 `TS2322`：函数声明返回 `T & Record<'tenantId' | 'userId', string>`，但 `return { ...where, [field]: scopeId }` 里的计算属性名让 TS 推出 `{ [x: string]: string }`，缺 `tenantId`/`userId`。
- 影响：`npx tsc --noEmit` 与 `npm run build`（`backend/Dockerfile:26` 的 builder 阶段）在 HEAD 上**均失败** → 生产镜像无法构建，与 OPT-25/OPT-26「生产工件与灾备演练已就绪」的结论相冲突。
- 修复：把 `field` 改为泛型 `K extends ScopeKey`，返回类型精化为 `T & Record<K, string>`（精确表达「被指定的那个键一定存在」，比原来的「两个键都存在」更诚实），仅保留一处必要的断言。`tsc` 与 `build` 恢复 0 错误。

### 2. `openapi.json` 与代码漂移（CI 阻断）

- `npm run openapi:check` 失败：实际 121 条路由，已提交文件 120 条。缺的是 T177 新增的 `GET /api/tenants/{id}/id-number`（明文查看接口），另有若干响应段顺序差异。
- 修复：`npm run openapi:generate` 重新生成并提交 `backend/openapi.json` 与 `frontend-admin/src/types/api.generated.ts`；`npm run openapi:check` 现在报「OpenAPI 121 条路由，与已提交文件一致」。

### 3. 证件号加密密钥变量名不一致（P0，运行时）

- 代码只读 `process.env.FIELD_ENCRYPTION_KEY`（`crypto.service.ts`、`encrypt-id-numbers.ts`），而 `backend/.env.example`、`docker-compose.prod.yml:68`、`docs/12 §1.1` 提供的都是 `ENCRYPTION_KEY`，且 `env.validation.ts` 只把它当「可选项」告警。
- 影响：按仓库自己的文档/compose 部署时，`CryptoService.key()` 取不到密钥 → `GET /api/tenants/:id/id-number`（查看证件号明文）抛 `未配置 FIELD_ENCRYPTION_KEY`。列表脱敏因 `maskStored` 内部吞掉异常而「看起来正常」，掩盖了问题。
- 为什么测试没发现：`field-crypto.spec.ts` 只测纯函数（密钥由参数传入），`tenants.service.spec.ts` 把 `CryptoService` 整个 mock 掉，**没有任何测试走过真实 `ConfigService` 接线**。
- 修复：
  1. `CryptoService` 改为注入 `ConfigService`，优先读 `ENCRYPTION_KEY`，保留 `FIELD_ENCRYPTION_KEY` 兼容别名；`encrypt-id-numbers.ts` 同步支持两名。
  2. 新增 `backend/src/common/crypto/crypto.service.spec.ts`（4 例）：`ENCRYPTION_KEY` 可用、旧名兼容、两名皆缺时抛错而非静默明文、解密失败抛错。
  3. `ENCRYPTION_KEY` 加入 `PRODUCTION_REQUIRED`（与 `docs/12` 的「✅ 必填」和 compose 的 `${ENCRYPTION_KEY:?}` 一致），生产缺失即拒绝启动。
