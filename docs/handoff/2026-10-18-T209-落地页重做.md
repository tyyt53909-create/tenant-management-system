## 一、问题定位：落地页比它展示的产品早冻结了 24 分钟

`landing/` 只被提交过一次（`41ca1ad`，2026-10-14 **20:13**），而把「栖居」设计语言套用到管理后台与
小程序的 `19261ab` 是同日 **20:37**——落地页在自己要展示的产品定稿之前就定型，此后产品每次改版它都没跟上。

由此暴露的三个层面问题：

1. **展示的是旧产品**：`assets/shots/*.jpg` 全部拍自栖居化之前（深色侧栏「租客管理系统」、蓝/绿/橙/红四色统计卡）。
   首屏 `<img>` 的 `alt` 还把旧数据写死在文字里（72 间 / 63 位 / 20 张）。
2. **手机 mockup 是旧小程序**：`--mp-primary:#1677ff` 微信蓝，且画了头像「陈嘉怡」与标题列——
   而现行小程序四个主页面都用 `navigationStyle:"custom"`，**根本没有标题列也没有头像**，品牌字是「栖居」。
3. **截图流水线已经跑不动**（这是「界面还是旧版」的根因，三处独立断裂，修一处不够）：
   - `capture_shots.py` 点的按钮名是「登录」，实际已改名 **进入运营中心**；
   - 它用 `wait_until="networkidle"` 等页面，而现行 Vite 页面永远到不了 networkidle → 30 秒逾时；
   - 截图用 `vite.screenshot.config.ts` **没有 Element Plus 按需引入插件**。T204 之后 `el-*` 组件不再在
     `main.ts` 全局注册，缺这组插件时页面渲染出来是空的（控制台一串 `Failed to resolve component: el-input`）；
   - 演示库 `tenant_demo` 只有 **26 张表 / 4 个已套用迁移**，现行 schema 是 29 张表 / 11 个迁移
     （缺 `invite_codes`、`job_runs`、`user_capability_overrides`）→ 就算脚本修好，旧库也喂不出新界面。

此外事实数字过时：「25 张数据表」实为 **28**、「17 个后端模块」实为 **20**；「项目现状」把已完成的三项
（覆盖率门禁、跨模块 e2e 回归、生产部署演练）挂在「进行中」，把已落地的智能水电表接入挂在「规划中」。

## 四、落地页重做

### 视觉语言

全面改用栖居令牌，与后台 `optimized-ui.css`、小程序 `qiju.css` 同源：暖白纸感底 `#f7f6f2` /
卡片 `#fffefa`、橄榄主色 `#515c43`、暖调阴影 `rgba(54,45,26,…)`、卡片圆角 13px。
深色区从原来的墨蓝（hue 268）换成**深橄榄炭 `#262a22`**，保留戏剧感但不跳出家族。
字体保留 Archivo 做拉丁与数字，中文回落系统栈，标题带产品同款的 `-.045em` 负字距。

### 信息架构：11 节重排为 9 节

合并 `roles` + `capabilities`（原本 3 张卡与 18 条一行文案讲同一件事）；把 `money` 重写为
**六步经营闭环**（签约 → 建账单 → 收款核销 → 抄表扣费 → 报修派单 → 退租结算），每步配真实截图；
合并 `screens` + `viewing`（公开看房页成为画廊第九个标签）；`status` 拆成「已跑通 / 已交付的工程能力 /
下一步」并补一张实测口径卡（28 张表、976 项测试、0 阻塞、121 条路由）。

品牌字从「租客管理系统 / 公寓·长租·二房东」改为 **栖居**（与两端产品一致）。

### 手机 mockup 依现行小程序重画

首屏那支改为现行首页结构：日期 eyebrow + `早上好，欢迎回家` + 铃铛 → 房源行 → 生活月历（含事件条）
→ 待处理事项 → 常用服务四宫格（**账单 / 合同 / 报修 / 余额**）。**移除头像、姓名与标题列**。
报修那支用真实的七态状态词（已提交/已受理/已派单/处理中/待确认/已完成/已取消）与真实类别
（家电维修 / 水管问题 / 电路问题）。令牌由微信蓝改为小程序真实值（`#68715b`、`#fffefa`、`#f5f2ec`、18px 圆角）。

### 深色区与对比度

审计脚本一开始报 **78 处** 对比度不达标：根因是三级墨色沿用了产品的 `--text-muted #8d9087`，
在暖白底上只有 3.0:1。改为同色相更深的 `#6a6d63`（暖白底 4.8:1、纸白 5.2:1）；
深色区的小号橄榄标签另备 `--primary-on-deep #8b9a78`（`--primary-light` 在深色底上只有 3.95:1）。
现在两种视角均是 **0 处不达标**。

### 本次顺带修好的校验脚本缺陷

- `verify_page.py` 把 `!i.complete` 当破图 → 懒加载图未滚到就被误判。改为「已加载却宽度为 0」才算破图，
  未加载的单独记 `imgsPending`；断言前先整页滚一遍（每个图最多等 3 秒——滚回顶部后视野外的懒图

  移动端检查原来读 `.stage__browser[data-stage]`（该属性已不存在），改为报告手机 mockup 的 `position`——
  正是本轮的真缺陷：窄屏下手机屏高随宽度暴涨，绝对定位会向上压住整段文案。

## 六、部署镜像里的落地页副本（验收时才发现）

使用者回報「還是舊版的」，查證後找到 repo 之外的另一份：

- **`http://localhost:8080/landing/` 是舊頁**，回傳標題仍是 `租客管理系统 — 公寓与长租的一体化管理后台`，
  檔案日期 `Oct 15 13:33`。原因是落地页在**建置時**被複製進前端映像
  （`frontend-admin/Dockerfile:19` `COPY landing /usr/share/nginx/html/landing`），
  跑的是 10/15 建置的 `tenant-web:local`——改 repo 不會影響它，必須重建映像。
- 已重建並重建容器：`docker compose -p tenant-prod -f docker-compose.prod.yml build web` →
  `up -d --no-deps web`。驗證：
  - `/landing/` 標題已是「栖居 · 收租、水电、报修、退租，收进同一本台账」，新章節存在；
  - 三张新截图的字节数与本地文件**逐字节一致**（dashboard 175186 / tenants 198036 / rooms 188798）；
  - 已删除的旧图 `meters.jpg` 返回 **404**（不再是残留）；
  - `/`（管理后台）标题已是「栖居管理 · PROPERTY CONSOLE」，本轮的前端修复一并生效；
  - 端口映射保持 `0.0.0.0:8080->8080`，postgres / redis 未被触碰（`--no-deps`）。

**运维缺口（建议后续处理）**：仓库里**没有** `.env.prod`（也不应在库里），而 `docker-compose.prod.yml`
对 `DB_PASSWORD` 等变量用的是 `${VAR:?…}` 必填插值——只插值就会直接中断（`required variable
DB_PASSWORD is missing`）。本次是从运行中的 postgres 容器 `Config.Env` 反查出真实值才跑通的。
也就是说：**没有一份本机的生产变量清单，任何人都无法重新部署这台栈**。建议把变量清单放到
仓库外（如 `~/.config/` 或密码管理器）并在 `docs/12-部署与运维.md` 写明位置。

## 七、遗留

1. **落地页没有 CI 门禁**。本轮新增的校验仍要靠人手跑 `verify_page.py` / `audit.py`。
   要不要把它接进 CI 是产品决定（它是一个纯静态目录，目前只在 nginx 以 `/landing/` 托管）。
2. **统计报表、楼栋管理、审计日志仍是旧样式**（`el-card` + 原生 Element 配色），因此**不入镜**。
   它们与栖居化页面的视觉落差是真实存在的，只是没有暴露在对外的页面上。
3. **仪表板「水电使用概览」卡未修**（沿用使用者决定）：它是**繁体中文**（水電/噸/塊）且数据取不到时
   fallback 到写死的演示数字并自标「演示数据」。本轮首屏取景避开了它，但它仍在真实工作台的首屏区域内。
4. 落地页品牌字改成了「栖居」。若对外仍要叫「租客管理系统」，改 `index.html` 的
   `.brand__text` 与 `main.js` 的 `COPY` 两处即可。
5. 只在 Chrome（Playwright `channel="chrome"`）下验证过；未跑 Safari / Firefox。
6. 演示数据是 2026-10 的快照。换月重跑种子不会再产生月份矛盾的文案，但页面上的示例数字
   （如 `¥1,910.00`）仍会与新一期账单不一致，需要一并重跑截图。
