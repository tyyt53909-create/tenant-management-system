## 一、生产部署不可重现：仓库里没有 `.env.prod`，也没有变量清单

- **现象（并行会话实测记录于 `docs/handoff/2026-10-18-T209-落地页重做.md`）**：`docker-compose.prod.yml` 用 `${VAR:?}` 做必填插值，而 `.env.prod` 按红线不入库 → 接手者不知道要哪些变量，只能从运行中的 postgres 容器反查真实值才跑通。「只有最初部署的那个人能重新部署」。
- **修复**：
  1. 仓库根目录新增 [`.env.prod.example`](../.env.prod.example)：完整占位模板（含「生产 seed 会拒绝默认邮箱/密码」等提示），真实值仍只在部署机/密码管理器；
  2. `docs/12 §7.5`「变量清单与接手部署」：列出 **compose 硬性要求的 7 个变量**（`DB_PASSWORD`、`JWT_SECRET`、`ENCRYPTION_KEY`、`ADMIN_EMAIL/PASSWORD`、`CLEANER_EMAIL/PASSWORD`）与有默认值的可选项，给出接手已有部署的最短路径；
  3. 同一节写明**换钥后果**：`ENCRYPTION_KEY` 一换，已加密的证件号将无法解密（密文只带 `v1:` 版本号，没有换钥迁移脚本）；`JWT_SECRET` 一换所有令牌立即失效。
- 注：`docs/12 §7.1/§7.2` 原本已有部署步骤与 `.env.prod` 模板，缺的是「必填项清单 + 接手路径 + 换钥红线」，本次补齐。

## 二、同房源唯一性落到数据库层

- **背景**：审查（T207）发现「同一房源可建多份未结束合同」会让同一房间重复出账（月账单幂等键是 `contractId+period`，不含 roomId）。当时只在应用层加了先查后写校验，我把它记为遗留项。
- **实测证据**：在本机 dev 库（`tenant_system`）上跑前置检查，**确实存在一笔**：房源 `cmv6h4ng800313klnef9dftdx` 同时有一份 `DRAFT` 与一份 `ACTIVE`。
- **修复**：
  1. 新迁移 `backend/prisma/migrations/20261018120000_one_unfinished_contract_per_room/migration.sql`：
     ```sql
     CREATE UNIQUE INDEX "idx_contracts_room_id_unfinished"
       ON "contracts" ("roomId") WHERE "status" IN ('DRAFT', 'ACTIVE');
     ```
     （Prisma schema 不支持部分唯一索引，故用原生 SQL；SQL 里写明了「库里有重复时本迁移会失败并报冲突」，不静默通过。）
  2. `check-duplicate-business-keys.ts` 增加第三类冲突：同一房源多份未结束合同，输出冲突房源与合同 id，并给出处理建议（保留生效的一份、删除多余草稿 —— docs/04 §2.2 允许删除 DRAFT）。纯读取，**不自动改数据**。
  3. `duplicate-keys.ts` 新增纯函数 `findDuplicateUnfinishedContracts()`（+3 个单测：同房源两份报冲突 / 不同房源不报 / 已结束状态不参与）。
  4. `docs/02 §2.6` 登记该约束与背景；`docs/12 §7.1` 部署步骤插入「已有数据时必做」的重复检查。
- **验证（不触碰你的 dev 数据）**：新建临时库 `scratch_t211` → `prisma migrate deploy` 全部套用成功 → SQL 实测：
  - 第一份 `ACTIVE`（房源 r1）✓ 成功；同一房源第二份 `DRAFT` → **`duplicate key value violates unique constraint "idx_contracts_room_id_unfinished"`** ✓ 被挡；
  - 另一房源 `ACTIVE` ✓ 成功；同一房源 `TERMINATED` ✓ 成功（证明是**部分**索引，不约束已结束合同）；
  - 验证后已 `DROP DATABASE scratch_t211`。

## 三、顺手修掉前置检查脚本的一个可用性问题

- **缺陷**：脚本头写的是 `npx tsx scripts/check-duplicate-business-keys.ts`，但用 tsx 直接跑**不会加载 `.env`**（Prisma CLI 会、客户端不会）→ 照文档跑会抛一长串 `PrismaClientInitializationError`（DATABASE_URL 未设置）。
- **修复**：脚本开头 `process.loadEnvFile?.()`（try/catch 容错，CI 已注入环境变量时忽略）。因为 Node 的 env 文件加载**不覆盖**已存在的变量，所以 `DATABASE_URL=... npx tsx ...` 这种显式指定的用法仍然优先 ✓。
