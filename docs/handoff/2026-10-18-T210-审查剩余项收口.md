## 一、上传原图的 EXIF/GPS 清理覆盖全部格式

- **缺陷**：`FilesService.save` 只对 JPEG 调 `stripMetadata`（sharp 重编码），PNG（`eXIf` chunk）与 WebP（EXIF chunk）**原样落盘**。T186/OPT-13 的验收写的是「上传图片…EXIF GPS 信息被移除」，实际只有缩略图与 JPEG 做到；手机相册的 PNG/WebP 坐标仍会随原图下载出去。
- **修复**：三种允许的格式统一走 `stripMetadata(body, format)`（sharp 默认不保留 metadata，PNG→png()、WebP→webp()、其余→jpeg(90)）。
  - 解不开的文件（magic bytes 像图片但内容不合法）**按原样保存并记 warn**，不再 500 —— 保持可用性；这类内容下载时带 `nosniff`，浏览器也不会当图片渲染。
- **测试**：两个 spec 里内嵌的「著名 1×1 PNG base64」本身不合规（实测 `vipspng: libpng read error`），也就是说**这条路径在测试里从来没真正跑过** —— 夹具换成 sharp 生成的真实 PNG 并**故意写入 EXIF**；新增 `files.service.spec` 一例断言「落盘 PNG 的 `metadata().exif` 为 undefined」，并先断言夹具自身带 EXIF（防「夹具本来就没有」的假通过）。
- **回归反证**：把修复还原成「只处理 JPEG」→ 该测试**失败**；还原后通过。
- **契约附件 spec** 的下载断言同步调整：原图会重编码，不再逐字节等于上传内容（改为断言格式/尺寸/EXIF 已清）。

## 二、账单列表静默忽略筛选参数

- **缺陷**：`bills.service.findAll` 只处理 `status/billType/contractId`，而 `QueryBillsDto` 声明的 `buildingId/startDate/endDate` 与导出接口 `exportBills` 全都支持 → 同一组参数下列表和导出**笔数不一致**，且不报错。
- **修复**：`findAll` 补齐 `buildingId`（`contract.room.buildingId`）与 `dueDate` 区间，与 `exportBills` 完全一致。
- **测试**：新增一例断言传参确实落到 `where`。

## 三、非法日期导致 500（应在边界回 400）

- **缺陷**：`QueryBillsDto`/`QueryCheckoutsDto`/`QueryPrepayTransactionsDto` 的 `startDate/endDate` 只用 `@IsString()` → `?startDate=abc` 通过校验，`new Date('abc')` 变成 Invalid Date 交给 Prisma → 500「服务器内部错误」。
- **修复**：三个 DTO 改 `@IsDateString()`（`QueryStatisticsDto` 与 `RenewContractDto` 本来就是对的），非法日期在 ValidationPipe 阶段回 400。
- **测试**：DTO 层由全局管道覆盖（既有 e2e/接口行为不变）。

## 四、`?isActive=false` 被当成 true

- **缺陷**：`QueryBuildingsDto.isActive` 用 `@Type(() => Boolean)`，`Boolean('false') === true` → 想筛「停用」的楼栋反而只返回启用中的。`tenants`/`notifications` 的 DTO 早已用 `@Transform` 修过同类问题（T156 实测），唯独这里漏了。
- **修复**：改 `@Transform(({ value }) => value === true || value === 'true')`，与另两处一致。
- **测试**：新增 `query-buildings.dto.spec.ts`（3 例）。**回归反证**：换回 `@Type(() => Boolean)` → `isActive=false` 那一例失败。

## 五、月账单 cron 与注释不符

- **缺陷**：`@Cron('0 10 1 * *')` 是 **5 段式**（分 时 日 月 周）→ 每月 1 日 **10:00** 触发；而注释与文档写的是 01:10，相邻两个 cron 都是含秒的 6 段式。
- **修复**：改为 `'0 10 1 * * *'`（01:10，与注释/文档一致）。

## 六、电表自动结算的基准未排除模拟读数

- **缺陷**：`meter-reading.service` 与 `meter-batch-reading.service` 的自动结算基准查询（找 `[SETTLED]`/`[INITIAL]` 读数为起点）没有 `source: NOT_SIMULATED` 过滤，而周期结算 `meter-billing.service` 有 —— 仿真器登记的起点会成为真实扣费基准，同一笔用量两条路径算出不同金额。
- **修复**：两处补上 `source: NOT_SIMULATED`，与周期结算统一。

## 七、租客端范围参数退化

- **缺陷**：9 处控制器用 `user.tenantId || user.userId || ''` 传范围。租客缺租客档案时，这个 fallback 会把 **userId** 当 tenantId 传给服务 —— 虽然查不出数据（不是泄漏），但语义错了，且掩盖了「本该 403」的事实（AGENTS.md §8.4 规则 2）。
- **修复**：全部改为 `user.tenantId ?? ''` → 空值时 `scopedWhere()` 直接抛 403。

## 七之补、收据/结算单归属检查的 fail-open（本轮一并修）

- **缺陷**：`bill-receipt.service.getReceipt` 与 `checkout.service.getVoucher` 的归属检查写成
  `if (tenantId && (!bill.contract || bill.contract.tenantId !== tenantId))`；控制器传的是
  `user.role === 'TENANT' ? user.tenantId : undefined`。一旦租客账号**没有租客档案**（tenantId 为
  undefined），整段比对被跳过 → 返回他人的收据/退租结算单（姓名、手机、房间、金额、扣款明细）。
- **修复**：
  - 两个控制器改为租客角色一律传 `user.tenantId ?? ''`（空串表示「租客但无档案」），只有管理员才传 `undefined`；
  - 两处服务判断改为 `tenantId !== undefined` —— 空串必须参与比对（对不上 → 404）。
- **测试**：两个 spec 各新增一例「tenantId 为空串 → 404」。**回归反证**：还原 `if (tenantId && ...)` → 该测试失败。

## 八、越权矩阵补齐

- **缺陷**：AGENTS.md §8.4 规则 3 要求租客端 GET 路由进矩阵，但 `GET /bills/my`、`/contracts/my`、`/maintenance/my`、`/prepay-accounts/my`、`/prepay-accounts/transactions` 都不在矩阵里；且矩阵里所有 TENANT 用例都带租客档案，「无租客档案」这一维度从未测过。
- **修复**：`authorization.e2e-spec.ts` 新增一个 describe（4 例）：5 条路由 × 「未登入 401 / CLEANER 403 / TENANT 200 且范围参数为自身 tenantId」，外加「TENANT 无租客档案 → 控制器传空范围」的接线断言（真实服务由 §七 的 `scopedWhere` 转成 403）。
  - 注：该 e2e 模块**没有** globalPrefix，路径不帶 `/api`；`prepay` 控制器的实际路径是 `prepay-accounts`。
