## M1 · 上線阻斷的安全與正確性（P0）

### OPT-01 OTP 驗證碼安全加固

- **現況**：`email-otp.service.ts` 的 `verifyCode` 只要 `NODE_ENV !== 'production'` 就接受 `123456`，部署時漏配 `NODE_ENV` 就等於留了一個後門。郵件發送失敗或未配 SMTP 時，驗證碼會用 `logger.warn` 明文寫進日誌。校驗失敗沒有次數上限。
- **做法**：萬能碼改成只在 `OTP_DEV_BYPASS=true` 且 `NODE_ENV=development` 同時成立時生效；生產環境禁止把驗證碼寫進日誌；未配 SMTP 時在生產環境直接拒絕發送並告警；單個驗證碼最多允許 5 次錯誤，超過就作廢；存儲底層抽成 `OtpStore` 接口，先用內存實現，OPT-08 再切到 Redis。

**驗收標準**

- [ ]  `NODE_ENV` 未設置或不是 development 時，`123456` 驗證失敗（單測覆蓋）
- [ ]  連續 5 次錯誤後，第 6 次即使輸入正確碼也失敗，必須重新發送
- [ ]  在 production 模式下觸發發信失敗，日誌裡搜不到 6 位驗證碼
- [ ]  現有 email-otp 單測全綠，新增至少 4 個安全測例

### OPT-02 全局與敏感接口限流

- **現況**：`@nestjs/throttler` 已經在依賴裡，但全倉庫沒有任何地方註冊。登入、OTP、註冊、邀請碼校驗、公開看房接口都可以被無限制請求。
- **做法**：註冊全局 `ThrottlerGuard`（例如 100 次/分鐘/IP），對敏感接口用 `@Throttle` 收緊：`/auth/login`、`/auth/login-email-code`、`/auth/google` 10 次/分鐘，`/auth/send-email-code` 5 次/小時/郵箱，`/auth/register`、`/auth/bind-invite-code` 10 次/分鐘。在反向代理後正確取得真實 IP（`trust proxy`）。存儲在 OPT-08 切到 Redis。

**驗收標準**

- [ ]  同一 IP 1 分鐘內第 11 次登入回傳 429，且帶 `Retry-After`
- [ ]  同一郵箱 1 小時內第 6 次發送 OTP 回傳 429
- [ ]  e2e 腳本和現有測試不受限流影響（測試環境可以調高閾值）
- [ ]  限流配置寫進 `docs/06-安全與合規清單.md`

### OPT-03 開發/模擬接口生產隔離

- **現況**：`POST /api/meters/simulator/run` 只限 ADMIN，但在生產環境仍然可用，會寫入真實讀數、觸發預付扣費。
- **做法**：新增 `FEATURE_METER_SIMULATOR` 開關（預設關閉），關閉時控制器回傳 404，前端「模擬器」入口按 `/auth/me` 或 `/config` 返回的開關隱藏。把模擬器產生的讀數標記為 `source = SIMULATED`，統計和結算都不計入。

**驗收標準**

- [ ]  開關關閉時請求模擬器回傳 404，後台看不到入口
- [ ]  開關打開時，模擬讀數不出現在結算和用量統計裡（單測覆蓋）
- [ ]  `.env.example` 與部署文檔登記該開關

### OPT-04 證件號欄位級加密

- **現況**：待確認清單 §9 已確認「證件號欄位級加密」，但 `TenantRegistration.idNumber` 是明文 `String`，代碼裡沒有任何加密邏輯。
- **做法**：新增 `CryptoService`（AES-256-GCM，金鑰來自 `FIELD_ENCRYPTION_KEY`，密文帶金鑰版本號）；增加 `idNumberHash` 欄位供精確查重；默認返回脱敏值，只有專用查看接口返回明文，並寫審計日誌；寫一個資料遷移腳本，把既有明文加密。

**驗收標準**

- [ ]  直接查資料庫只看得到密文，看不到任何明文證件號
- [ ]  列表和詳情接口只返回脱敏值（如 `4401********1234`）
- [ ]  每次查看明文都產生一条 `VIEW_ID_NUMBER` 審計記錄
- [ ]  遷移腳本可以重複執行（冪等），且有回滾說明

### OPT-05 關鍵業務 DB 唯一約束（冪等）

- **現況**：`Bill` 只有普通索引，月度租金賬單靠 `findFirst` 先查後寫來去重，並發或多實例下會生成重複賬單。通知提醒也是同樣的做法。
- **做法**：盤點所有「先查後寫」的地方，為租金賬單加部分唯一索引 `(contractId, billType, period)`，為提醒類通知加 `dedupeKey` 唯一鍵，為設備讀數加 `(meterId, messageId)` 唯一鍵；程式捕捉 `P2002` 當成「已存在」。上線前先跑重複數據檢查腳本。

**驗收標準**

- [ ]  並發 10 個請求同時生成同一月度賬單，最終只有 1 条（整合測試）
- [ ]  Migration 在有重複數據的庫上會先報告衝突，而不是靜默失敗
- [ ]  文檔 `02-數據模型.md` 登記新約束

### OPT-06 資料範圍查詢統一治理（Prisma undefined 陷阱）

- **現況**：待確認清單 §28：`where: { tenantId: undefined }` 會退化成全表查詢，這就是 §27 高危越權的成因。目前只是各處自己判空，沒有統一機制。
- **做法**：新增 `ScopeService` 或 `@CurrentScope()` 裝飾器，統一產生 `{ tenantId }` / `{ buildingId }` 過濾條件，缺少時直接拋出 403；用 Prisma Client Extension 對租客敏感模型檢查 where 中的範圍鍵是否為 undefined；補一個「全路由越權矩陣」測試，用 3 種角色 × 有/無檔案跑遍所有 GET 路由。

**驗收標準**

- [ ]  所有租客端查詢都經過統一的範圍助手，`grep` 不到手寫的 `tenantId: user.xxx` 過濾
- [ ]  對租客敏感模型傳入 undefined 範圍鍵時拋錯，而不是返回全表
- [ ]  越權矩陣測試覆蓋 100% 的 GET 路由，並在 CI 中執行
- [ ]  規則寫進 `AGENTS.md`

### OPT-07 啟動時環境變量校驗

- **現況**：只有 `JWT_SECRET` 有校驗；`.env.example` 缺 `CLEANER_EMAIL`、`UPLOAD_DIR`、SMTP 系列、`GOOGLE_CLIENT_ID` 等。
- **做法**：用 zod（或 Joi）在 `ConfigModule.forRoot({ validate })` 中校驗全部變量，生產環境缺必填項就拒絕啟動；一律改用 `ConfigService`，不再直接讀 `process.env`；補全 `.env.example`。

**驗收標準**

- [ ]  生產模式缺任一必填變量時，進程啟動失敗並列出缺失的變量名
- [ ]  `src/` 中除 config 層外沒有 `process.env` 讀取
- [ ]  `.env.example` 與部署文檔 §1 變量清單一致（docs-check 校驗）

## M2 · 後端基礎設施與共享狀態

### OPT-08 接入 Redis 作為共享狀態

- **現況**：Compose 和 CI 都起了 Redis，但代碼完全沒有用到；OTP 存在進程內存，重啟就丟失，多實例之間不互通。
- **做法**：新增 `RedisModule`（ioredis），用於 OTP 存儲（TTL）、限流存儲、分佈式鎖、熱點快取（儀表板）；未配 `REDIS_URL` 的開發環境退回內存實現。

**驗收標準**

- [ ]  後端啟 2 個實例，實例 A 發的 OTP 可以在實例 B 驗證通過
- [ ]  重啟後端後，未過期的 OTP 仍然有效
- [ ]  Redis 不可用時，`/health` 報告 degraded，核心 CRUD 仍然可用

### OPT-09 Refresh Token 輪換與撤銷

- **現況**：Refresh Token 是無狀態 JWT，只能等它自己過期；沒有登出失效、也沒有偷用檢測。
- **做法**：新增 `RefreshSession` 表（或 Redis）存 `jti`、設備、過期時間；每次刷新都輪換，舊 token 再次使用時視為偷用，整個會話族失效；新增 `POST /auth/logout` 與「登出所有設備」；管理員禁用帳號時一併清掉會話。

**驗收標準**

- [x]  登出後用舊 refresh token 刷新回傳 401（T182）
- [x]  同一個 refresh token 使用兩次，第二次失敗，且該用戶所有會話失效（T182）
- [x]  後台和小程序的自動刷新都能處理輪換後的新 token（前端測試覆蓋，T182）

### OPT-10 定時任務多實例安全

- **現況**：`@Cron` 直接跑在每個後端實例裡，擴容就會重複生成賬單和通知。
- **做法**：用 PostgreSQL advisory lock（或 Redis 鎖）包住每個 job；新增 `JobRun` 表記錄開始/結束/結果/錯誤摘要；提供管理員「手動重跑」接口；補上「通知保留 180 天」的清理 job（已確認但未實現）。

**驗收標準**

- [x]  2 個實例同時觸發月度賬單 job，只有一個實際執行，另一個記錄 skipped（T183）
- [x]  每次 job 執行在 `JobRun` 中都有記錄，失敗時有錯誤摘要（T183）
- [x]  超過 180 天的通知會被清理（單測覆蓋，T183）

### OPT-11 全局異常過濾器與統一錯誤碼

- **現況**：`common/filters`、`common/interceptors` 是空目錄。錯誤格式依賴 Nest 預設行為，Prisma 異常（例如 P2002、P2025）可能直接變成 500。前端只能靠文案來判斷錯誤類型（`CAPABILITY_DENIED` 是唯一的例外）。
- **做法**：定義錯誤碼枚舉（`AUTH_*`、`BILL_*`、`ROOM_STATE_*` 等），統一回應 `{ code, message, details?, requestId }`；將 Prisma 已知錯誤映射成 409/404；未知錯誤只回通用訊息，細節寫日誌。

**驗收標準**

- [ ]  所有 4xx/5xx 回應的 JSON 結構一致，且都帶 `code` 和 `requestId`
- [ ]  唯一鍵衝突回 409，而不是 500
- [ ]  生產環境 500 回應不洩露堆棧或 SQL
- [ ]  前端 `request.ts` 和小程序改成按 `code` 提示錯誤

### OPT-12 結構化日誌、requestId、健康檢查

- **做法**：接入 `nestjs-pino`（JSON 日誌，自動脱敏 `authorization`、`password`、`code`）；每個請求生成或透傳 `X-Request-Id`；新增 `/api/health`（liveness）與 `/api/health/ready`（DB / Redis / 磁盤）；可選接入 Sentry。

**驗收標準**

- [ ]  每条請求日誌都含 `requestId`、`userId`、耗時、狀態碼
- [ ]  日誌中搜不到密碼、token、驗證碼
- [ ]  停掉資料庫後 `/health/ready` 回 503，`/health` 仍回 200

### OPT-13 文件存儲抽象（本地 / OSS）與縮略圖

- **現況**：`files.service.ts` 直接寫本地磁盤，多實例無法共享。已確認「服務端生成縮略圖」，但代碼沒有實現（`thumbnail` 欄位由前端傳入）。
- **做法**：定義 `StorageAdapter`（put / get / delete / signedUrl），實現 `LocalStorage` 與 `S3CompatibleStorage`（阿里雲 OSS / MinIO）；上傳時用 sharp 生成縮略圖並去掉 EXIF；校驗真實 MIME（magic number）。

**驗收標準**

- [ ]  切換 `STORAGE_DRIVER=local|s3` 不需改業務代碼
- [ ]  上傳圖片自動產生縮略圖，EXIF GPS 資訊被移除
- [ ]  改副檔名偽裝的非圖片文件被拒絕
- [ ]  歸屬校驗（T159）行為不變，原有測試全綠

### OPT-14 擴展點接口落地

- **現況**：`docs/01-架構設計.md` §5 設計了 `IMeterAdapter`、通知渠道抽象、支付接口預留，代碼裡一個都沒有。通知只能直接寫站內通知表。
- **做法**：只建接口與預設實現，不接第三方：`NotificationChannel`（先實現 InApp、Email）與 `NotificationDispatcher`（依優先級和偏好選渠道）；`MeterAdapter`（Manual、Simulator）；`PaymentProvider`（Offline）。業務代碼改成只依賴接口。

**驗收標準**

- [ ]  業務模組不再直接寫 `prisma.notification.create`，而是經過 Dispatcher
- [ ]  新增一個渠道只需要實現接口並註冊，不改業務代碼（有空渠道示例與單測）
- [ ]  架構文檔 §5 與代碼一致

## M3 · 代碼結構、類型與前端

### OPT-15 OpenAPI 文檔與前端類型自動生成

- **現況**：已確認「前後端類型共享，OpenAPI 自動生成」，但後端沒有 Swagger，後台 `src/types/index.ts` 是手寫的，小程序是 JS；`docs/05-接口規範.md` 靠人工同步，已經發生過多次不一致。
- **做法**：接入 `@nestjs/swagger`（CLI plugin 自動讀 DTO），生成 `openapi.json` 提交入庫；用 `openapi-typescript` 生成前端類型，去掉手寫類型；CI 檢查 openapi.json 是否和代碼一致；非生產環境開放 `/api/docs`。

**驗收標準**

- [ ]  所有 85+ 條路由都出現在 OpenAPI 中，含請求/回應結構和鑑權要求
- [ ]  後台不再有手寫的接口 DTO 類型，`vue-tsc` 全綠
- [ ]  改 DTO 但未重新生成 openapi.json 時 CI 失敗
- [ ]  `docs/05` 改為指向 OpenAPI，只保留約定類說明

### OPT-16 拆分超大 service / controller

- **現況**：`meters.service.ts` 1416 行（錄入、批量、匯出、扣費、看板、結算都在一個類裡）；`bills.service.ts` 838 行；`auth.controller.ts` 592 行且直接注入 `PrismaService`，違反架構文檔 §3.2 的單向依賴規則。
- **做法**：meters 拆成 `MeterService`、`MeterReadingService`、`MeterBillingService`（扣費/結算）、`MeterUsageQueryService`（看板/匯出）；bills 拆出 `BillPaymentService`、`LateFeeService`、`ReceiptService`；auth 的業務邏輯下沉到 `AuthService` / `RegistrationService`。拆分只搬代碼，不改行為。

**驗收標準**

- [ ]  沒有任何 service 或 controller 超過 500 行（可加入 lint 規則 `max-lines`）
- [ ]  controller 不再注入 `PrismaService`（可用架構測試或 lint 校驗）
- [ ]  593 個既有後端測例不改斷言且全綠，e2e-mvp 27 項斷言全綠

### OPT-17 類型安全治理

- **現況**：後端 `src` 有 128 處 `any` / `as any`，包括 `@Request() req: any`、`(tx as any).$executeRawUnsafe`。

### OPT-20 管理後台 Token 存儲加固
