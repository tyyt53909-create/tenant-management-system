# 租客管理系统 - 权限矩阵

> 版本: v0.2  
> 更新: 2026-10-15

---

## 1. 角色定义

| 角色 | 标识 | 说明 | 数量 |
|------|------|------|------|
| **管理者** | ADMIN | 房东或授权管理人员，拥有所有权限 | 1人 |
| **保洁** | CLEANER | 负责房间清洁，权限受限 | 多人（用标签区分员工/外包） |
| **租客** | TENANT | 租住的房客，只能访问自己的数据 | 多人 |

**说明**：
- 角色存储在 `User.role` 枚举字段
- 标签（tags）仅用于标记和筛选，不影响权限判断
- 第一版无"维修方"角色，维修记录由管理者手动维护

## 2. 数据范围隔离

### 2.1 Building 隔离（第一版硬编码）

| 角色 | 数据范围 |
|------|----------|
| 管理者 | 固定为 `default-building`（第一版硬编码） |
| 保洁 | 固定为 `default-building` |
| 租客 | 固定为 `default-building` |

**实现方式**：
```typescript
// auth/guards/building.guard.ts
@Injectable()
export class BuildingGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    // 第一版：所有用户默认访问 default-building
    request.buildingId = 'default-building';
    return true;
  }
}
```

**第二阶段扩展**：
- 管理者关联到多个楼栋（通过中间表 `user_buildings`）
- 保洁和租客权限不变（只能访问自己所在楼栋）
- 所有查询自动注入 `WHERE building_id IN (user.accessibleBuildings)`

### 2.2 租客数据隔离

| 角色 | 可访问的租客数据 |
|------|------------------|
| 管理者 | 所有租客 |
| 保洁 | 不可访问租客信息 |
| 租客 | 只能访问自己的数据（通过 `User.tenantId` 关联） |

**实现方式**：
```typescript
// 租客访问自己的合同
async findMyContracts(userId: string) {
  const user = await this.prisma.user.findUnique({
    where: { id: userId },
    include: { tenant: true },
  });
  
  if (!user.tenant) {
    throw new ForbiddenException('Not a tenant');
  }
  
  return this.prisma.contract.findMany({
    where: { tenantId: user.tenant.id },
  });
}
```

```typescript
// GET /rooms - 查看房间列表
@Get()
@UseGuards(JwtAuthGuard, RolesGuard)
async findAll(@CurrentUser() user: User, @Query() query: RoomQueryDto) {
  if (user.role === UserRole.ADMIN) {
    // 管理者：查看所有房间
    return this.roomsService.findAll(query);
  } else if (user.role === UserRole.CLEANER) {
    // 保洁：仅查看待清洁房间
    return this.roomsService.findPendingCleanRooms(query);
  } else if (user.role === UserRole.TENANT) {
    // 租客：仅查看自己租住的房间
    return this.roomsService.findMyRooms(user.tenant.id);
  }

// PATCH /rooms/:id/clean - 标记已清洁
@Patch(':id/clean')
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(UserRole.ADMIN, UserRole.CLEANER)
async markAsClean(@Param('id') id: string, @CurrentUser() user: User) {
  return this.roomsService.markAsClean(id, user.id);
}
```

## 4. 特殊权限场景

### 4.1 邀请码机制

| 操作 | 说明 |
|------|------|
| 生成邀请码 | 管理员按需生成（默认 365 天有效），角色可取 `TENANT` / `CLEANER` / `ADMIN` |
| 使用邀请码 | 仅用于绑定**已预建**租客档案，或给已有账号补充角色；不自动创建租客档案（DEC-03） |
| 验证邀请码 | 校验：是否存在、是否过期、是否已使用 |
| 邀请码失效 | 使用后立即失效（原子核销，并发只有一个成功），到期自动失效 |

**注册策略（DEC-03，T260）**：

- 禁止自助成为租客：邮箱 OTP / Google 首登必须有有效邀请码，且系统中存在 `userId = null` 且邮箱精确匹配的 `Tenant`。
- 密码注册同样要求预建档案；不再创建 `Tenant`，也不再生成 `pending-` 占位手机号。
- 邀请码的 `role` 在建号/绑定时生效；非 `TENANT` 账号不能被他角色邀请码改写（返回 409）。

### 4.2 公开看房页

| 资源 | 权限 |
|------|------|
| 房间列表（空置） | 公开，不需要登录 |
| 房间详情（空置） | 公开，但不显示租金和押金 |
| 房源照片 | 公开；走 `GET /api/public/files/:key`（仅 `visibility=PUBLIC`），私有对象 404 |
| 房间设施 | 公开 |
| 租客信息 | 不返回任何租客信息 |
| 合同信息 | 不返回 |

**限流策略**：
- 100 次/分钟/IP
- 超过限流返回 429 Too Many Requests

### 4.3 审计日志访问

| 场景 | 权限控制 |
|------|----------|
| 查看所有日志 | 仅管理者 |
| 查看证件信息日志 | 记录每次访问 `TenantRegistration` 表的操作 |
| 查看敏感操作日志 | 收款、退款、账户调整等操作必须记录 |
| 导出日志 | 仅管理者，且需记录导出行为本身 |

## 5. 权限实现方式

### 5.1 装饰器

```typescript
// auth/decorators/roles.decorator.ts
export const Roles = (...roles: UserRole[]) => SetMetadata('roles', roles);

// auth/guards/roles.guard.ts
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.get<UserRole[]>('roles', context.getHandler());
    if (!requiredRoles) {
      return true;
    }
    
    const request = context.switchToHttp().getRequest();
    const user = request.user;
    
    return requiredRoles.some(role => user.role === role);
  }
}
```

### 5.2 使用示例

```typescript
// rooms.controller.ts
@Controller('rooms')
@UseGuards(JwtAuthGuard, BuildingGuard)
export class RoomsController {
  // 所有角色可访问（需登录）
  @Get()
  async findAll(@CurrentUser() user: User) {
    return this.roomsService.findAllByRole(user);
  }

  // 仅管理者和保洁可访问
  @Patch(':id/clean')
  @Roles(UserRole.ADMIN, UserRole.CLEANER)
  @UseGuards(RolesGuard)
  async markAsClean(@Param('id') id: string) {
    return this.roomsService.markAsClean(id);
  }

  // 仅管理者可访问
  @Post()
  @Roles(UserRole.ADMIN)
  @UseGuards(RolesGuard)
  async create(@Body() dto: CreateRoomDto) {
    return this.roomsService.create(dto);
  }
}
```

### 5.3 服务层权限过滤

```typescript
// contracts.service.ts
async findAll(user: User, query: ContractQueryDto) {
  const where: Prisma.ContractWhereInput = {
    buildingId: user.buildingId,  // Building 隔离
  };

  if (user.role === UserRole.TENANT) {
    // 租客只能查看自己的合同
    where.tenantId = user.tenant.id;
  }

  return this.prisma.contract.findMany({
    where,
    include: { room: true, tenant: true },
  });
}
```

### 5.4 全域默认拒绝（T257 / SEC-01）

`JwtAuthGuard` 与 `RolesGuard` 在 `AppModule` 中通过 `APP_GUARD` 全局注册，执行顺序为「限流 → JWT → 角色」：

| 场景 | 结果 |
|------|------|
| 未标注 `@Public()` | 必须携带有效 Bearer Token，否则 401 |
| 类或方法标注 `@Public()` | 跳过 JWT 校验，无需登录 |
| 已登录但未标注 `@Roles()` | 放行（角色不限） |
| 已登录且标注 `@Roles(...)` | 角色不符返回 403 |

**维护规则**：

1. 新增公开接口必须在控制器类或方法上显式标注 `@Public()`，并更新 `backend/src/common/guards/route-policy.spec.ts` 的 `PUBLIC_ROUTE_ALLOWLIST`（当前 16 条）。
2. `backend/test/route-policy.snapshot.json` 锁定全部路由的 `method / path / public / roles`（当前 142 条）。路由变化会让测试失败；确认预期后运行
   `UPDATE_ROUTE_SNAPSHOT=1 npx vitest run src/common/guards/route-policy.spec.ts` 更新快照并随代码提交。
3. 控制器/方法上遗留的 `@UseGuards(JwtAuthGuard, RolesGuard)` 保留为纵深防御，不改变默认拒绝语义。
4. `@Public()` 与 `@Roles()` 不得同时出现在同一条路由上，测试会拦截。

## 6. 敏感操作审计

所有以下操作必须记录审计日志：

| 操作类型 | 记录内容 |
|----------|----------|
| 创建/修改/删除合同 | 操作人、时间、IP、变更内容（before/after） |
| 确认收款 | 操作人、时间、金额、账单ID |
| 添加滞纳金 | 操作人、时间、建议金额、确认金额 |
| 预付账户充值/调整 | 操作人、时间、金额、原因 |
| 修改水电单价 | 操作人、时间、旧单价、新单价、生效日期 |
| 查看证件信息 | 操作人、时间、租客ID |
| 发起/确认退租 | 操作人、时间、合同ID、退款金额 |
| 创建/禁用用户 | 操作人、时间、目标用户、角色 |

**实现方式**：
```typescript
// audit/audit.interceptor.ts
@Injectable()
export class AuditInterceptor implements NestInterceptor {
  constructor(private auditService: AuditService) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request = context.switchToHttp().getRequest();
    const user = request.user;
    const action = context.getHandler().name;
    const entityType = context.getClass().name.replace('Controller', '');

    return next.handle().pipe(
      tap(result => {
        if (this.isSensitiveOperation(action)) {
          this.auditService.log({
            userId: user.id,
            action,
            entityType,
            entityId: result?.id,
            changes: this.extractChanges(request.body, result),
            ip: request.ip,
            userAgent: request.headers['user-agent'],
          });
        }
      }),
    );
  }
}
```

### 7.2 细粒度权限（RBAC）

如果需要更细粒度的权限控制（如"只读管理者"），可引入 RBAC：

```typescript
model Permission {
  id       String @id
  resource String  // "contracts"
  action   String  // "read", "write", "delete"
}

model RolePermission {
  roleId       String
  permissionId String
  
  @@id([roleId, permissionId])
}
```

**第一版不实现**，保持简单的角色权限即可。

### 7.3 租客账号能力开关与登入控制（T173）

为满足管理后台对个别租客的登录限制与功能屏蔽诉求，本系统在角色与租客档案之外，引入独立的**账号状态**与**功能能力覆写**机制：

#### 7.3.1 三层分离原则

| 层次 | 字段 / 数据源 | 业务含义 | 影响机制 |
|---|---|---|---|
| **档案状态** | `Tenant.isActive` | 该租客档案是否在租生效 | 后台列表启用/停用租客，控制租赁合同建立 |
| **登录账号状态** | `User.isActive` | 用户能否登入、旧凭据是否有效 | `JwtStrategy` 每次验证时核对 `User.isActive`，禁用后旧 token 立即失效 (401) |
| **功能能力覆写** | `UserCapabilityOverride` | 登入后能使用哪些租客端功能 | `CapabilityGuard` 检查 `DENY` 覆盖，拦截返回 403 `CAPABILITY_DENIED` |

#### 7.3.2 能力清单与生效规则

能力清单由后端代码（`TenantCapabilityCatalog`）硬编码定义，不设自由开放字典。第一版支持 6 项租客能力：

| 能力代码 | 显示名称 | 默认规则 | 受保护接口 |
|---|---|---|---|
| `tenant.contract.read` | 查看自己的合同与附件 | 允许 | `GET /contracts/my`、`GET /contracts/:id`、`GET /contracts/:id/attachments`、`GET /contracts/:id/attachments/:attachmentId/file` |
| `tenant.bill.read` | 查看自己的账单与收据 | 允许 | `GET /bills/my`、`GET /bills/:id`、`GET /bills/:id/receipt` |
| `tenant.prepay.read` | 查看自己的预付账户与流水 | 允许 | `GET /prepay-accounts/my`、`GET /prepay-accounts/transactions` |
| `tenant.maintenance.read` | 查看自己的报修工单 | 允许 | `GET /maintenance/my`、`GET /maintenance/:id` |
| `tenant.maintenance.create` | 提交报修工单 | 允许 | `POST /maintenance` |
| `tenant.checkout.read` | 查看自己的退租结算 | 允许 | `GET /checkout`、`GET /checkout/:id`、`GET /checkout/:id/voucher` |

**判定逻辑**：
1. 若用户角色不是 `TENANT`：守卫直接放行（管理者不受此限制）。
2. 若能力代码不在官方目录中：直接拒绝。
3. 若存在该用户的 `DENY` 覆写记录：拒绝（抛出 403 `CAPABILITY_DENIED`）。
4. 若存在 `ALLOW` 记录：放行。
5. 否则采用目录默认策略（第一版全量能力默认放行）。

#### 7.3.3 不可屏蔽项与安全红线

- **通知不可屏蔽**：`tenant.notification.read`（包含催租与工单流转通知）必须送达租客，不可配置屏蔽。
- **个人中心不可屏蔽**：`GET /tenants/:id` 允许租客查看个人档案，不可配置屏蔽。
- **数据隔离绝不放宽**：能力开关只能收紧权限，绝不提升用户角色为 `ADMIN`/`CLEANER`，租客无论如何覆写都仅能访问属于本人的数据范围（`tenantId` 硬隔离）。
- **未注册档案不可预设**：未注册绑定 `User` 的租客档案不能预写权限，也不会自动建账号。`GET /tenants/:id/account` 与 `GET /tenants/:id/capabilities` 返回 200 和 `{ status: "UNREGISTERED" }`。`PATCH /tenants/:id/account` 与 `PUT /tenants/:id/capabilities` 返回 409 Conflict。

## 8. 验收标准

### 8.1 功能验收
- [ ] 每个角色只能访问权限矩阵定义的资源
- [ ] 租客无法访问其他租客的数据
- [ ] 保洁只能查看待清洁房间列表，不能查看租客信息
- [ ] 公开看房页不泄露任何租客和合同信息

### 8.2 安全验收
- [ ] 所有敏感操作有审计日志
- [ ] 列表接口默认不返回敏感字段（手机号、邮箱脱敏）
- [ ] 证件信息查看有审计日志
- [ ] 权限绕过测试通过（尝试越权访问被阻止）

### 8.3 性能验收
- [ ] 权限过滤在数据库层完成（WHERE 子句），不在应用层遍历
- [ ] Building 隔离查询有索引支持
- [ ] 租客数据隔离查询 < 50ms
