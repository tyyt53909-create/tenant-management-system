## T335 的增量模型与行为

本 PR 为 expand 步骤。`UtilityPolicyVersion` 保存合同及费用类型的不可变版本、明确选择的三种 collectionMode、六位小数的分额费率、单位、生效读数时点、确认人及依据。计算范围为 `METER_DELTA_FLAT_RATE`，舍入为 `HALF_UP_CHARGE_V1`，先以 decimal 合计再取整分。新增版本的生效点递增；相同规则的相邻段复用原版本。跨已有版本的责任段需在切点拆分。

`MeterResponsibilityInterval` 在本阶段只登记有真实起点、终点的闭合段，消费时间采用 `[startAt,endAt)`，起终读数差计算本段用量。相邻段可共享边界读数。TENANT 必须解析为指定合同及租客；OWNER 仅能登记已确认空置或无租约覆盖的区间。租客归属复用 T328 的交接事实解析，冲突及缺交接返回阻断。未来、模拟、乱序回退、跨物理表交接需先处理原问题。责任字段及读数以服务器资料确定。

数据库使用 `btree_gist` 及排他约束防止同表责任段重叠，另有起终时间、租客/房东字段形状、非负费率和版本唯一约束。部署迁移账号需具有安装 PostgreSQL 自带 `btree_gist` 扩展的权限。迁移可重跑，既有财务表保持原金额和来源。新表为空，存量规则通过管理者逐项核验后产生。

`UtilityRuleConfirmation` 保存 UUID 请求键、规范化资料哈希与原结果。相同请求重放返回原结果，异内容返回 `IDEMPOTENCY_CONFLICT`。规则、责任段、审计、重放结果同事务提交。预览的 SHA-256 包括实际表计、租约、区间读数、旧规则、已有责任段、账户和流水；确认锁内重读，变化返回 `PREVIEW_STALE`。阻断详情通过 `UTILITY_RULE_BLOCKED` 的 `details.blockingIssues` 返回。

核验接口返回 `financialPostingEnabled=false` 和 `financialEffect=NONE`。三种模式仅呈现试算。预付缺账户或账实不符另列 billingIssues，可以保存已核对的规则，正式计费仍需解除阻断。规则确认产生的纪录供下一步计费切换使用，正式资金授权仍需对相应费用及政策验收。

已核验某合同/费用类型的规则后，该项的既有即时、单表、批量与周期表计结算统一返回 `BLOCKED / RULE_POSTING_NOT_ENABLED`，保留原游标。该切换隔离防止后付或直缴继续被旧预付引擎收费。缺规则的存量处于原路径，本阶段的盘点逐项列出 LEGACY_REVIEW_REQUIRED；新规则正式计费及全部旧入口收口仍需后续切换 PR。

## API 与最小操作

所有新路由仅 ADMIN 可用，租客、保洁及匿名身份被后端拒绝。

| 路由 | 功能 |
|---|---|
| `GET /api/utility-readiness/contracts/:id` | 合同各表的已确认规则、责任段、最近 100 笔真实读数、游标及缺失条件 |
| `GET /api/utility-readiness/inventory?buildingId=&afterId=` | 每页最多 200 份非草稿合同的未核验表计，nextCursor 接续 |
| `POST /api/utility-readiness/preview` | 核对指定起终读数、归属与费率，返回只读试算和 reviewToken |
| `POST /api/utility-readiness/confirm` | 明确确认证据，要求 requestId 与 reviewToken |

管理后台合同的「更多操作 → 水电规则与交接」可完成选表、责任人、真实边界、模式、精确费率和依据填写。必须先检查预览，再点「确认规则与责任」。合同号筛选已接入后端校验及查询，管理端可直接定位目标合同。修改资料会使页面预览失效。网络响应丢失时，刷新后用原请求重试，确认结果及原金额可查。

## 写入口与共同锁迁移

T335 的规则确认顺序为请求 advisory lock → room → contract → meter → 确认记录。预览和盘点采用 RepeatableRead 只读查询。现有资金路径仍使用各自已验证的锁；整个系统采用统一 room 协调的切换门禁尚待下列路径联合验证。

| 现有入口 | 当前机制 | 后续切换要求 |
|---|---|---|
| `meter-reading.service`、`meter-batch-reading.service`、`meter-billing.service` | T326 表计锁、全局游标；T328–330 归属与报价 | 接责任段、规则版本和唯一正式 Charge，覆盖人工/批量/设备 |
| `periodic-charges.service` | T333 持久条目、逐项事务、预览指纹 | 采用同一 Charge 及模式，明确新版结果迁移 |
| `bill-payment.service` 的收款、作废、预付支付及退款回调 | T325 帐单写锁与事务 | 资金保留及房间协调，区分冲正和正常退押金 |
| `prepay.service`、支付充值回调及人工调整 | 条件余额更新、流水和原去重机制 | 可用额扣除保留款、租期关闭及晚到入账 |
| `deposit-ledger.util` 及押金模块 | 原押金流水及余额 | 抵扣分配、保留与实际付款证据 |
| `contracts.service`、`move-ins.service`、续签及自动激活 | T331 房间协调、T332 一次入住事务 | 新规则及开放责任段、续租连续性 |
| `checkout.service` 的完成动作 | 原结算事务与房态/保洁 | 权威预览、尾费、资金分配、实际腾房及退款 |
| `public-utilities.service` 的分摊出账 | allocation 去重及既有分摊事务 | 历史责任、模式、来源覆盖、参与房间排序锁 |
| `imports.service` 的历史账单写入 | 历史导入事务 | 限定历史迁移范围并独立核账 |
| `scheduler-monthly-bills.service`、补办及管理脚本 | 原租金幂等和排程 | outbox 同事务、当前有效提醒、漏账补办 |

后续切换必须同时覆盖上表入口。目标顺序为 room → contract → meter → responsibility/coverage → bill → prepay → deposit → checkout/payout，多个同类对象按 ID 排序。完整 X-04 财务交错与锁等待验证后，才可将该顺序作为全局已落地契约。
