# ADR-001: 后端技术栈选型

## 状态
已接受 (2026-10-11)

## 背景
项目需要选择后端技术栈，用户倾向 TypeScript(NestJS) + Prisma/TypeORM + PostgreSQL，理由是前后端同语言、结构强制模块化便于廉价模型照样板实现。需要从五个维度对比 TypeScript(NestJS) vs Python(FastAPI) 并给出最终推荐。

## 决策维度对比

### 1. 类型安全与开发效率

**TypeScript + NestJS**
- ✅ 编译时类型检查，IDE 智能提示完整
- ✅ 装饰器语法清晰，依赖注入成熟
- ✅ 前后端共享类型定义（DTO、Entity）
- ✅ Prisma 生成的类型直接可用
- ⚠️ 装饰器和元数据较多样板代码

**Python + FastAPI**
- ✅ Pydantic 提供运行时验证和类型提示
- ✅ 类型标注简洁（Python 3.10+ 语法友好）
- ⚠️ 运行时才能发现类型错误
- ⚠️ 前后端类型不共享，需维护两套

**结论**: TypeScript 在类型安全上有编译时优势，前后端类型共享减少重复定义。

---

### 2. AI 辅助编程友好度（多模型协作场景）

**TypeScript + NestJS**
- ✅ 结构高度规范化：Controller → Service → Repository 三层清晰
- ✅ 装饰器明确标记路由、依赖、验证，AI 易识别意图
- ✅ 模块（Module）强制边界，廉价模型按样板实现不易越界
- ✅ OpenAPI 装饰器直接生成文档，AI 可直接阅读规范
- ✅ GitHub Copilot / Cursor 对 NestJS 模式识别率高
- ⚠️ 配置文件较分散（module、controller、service、dto、entity）

**Python + FastAPI**
- ✅ 代码简洁，文件数少，单个文件即可定义完整路由
- ✅ 函数式路由定义直观，AI 易生成
- ⚠️ 灵活度高但缺乏强制结构，廉价模型容易写出不一致的代码
- ⚠️ 依赖注入需手动管理或用第三方库（如 dependency-injector）
- ⚠️ 模块化依赖开发者自律，无框架级约束

**结论**: NestJS 的强制模块化和装饰器驱动架构更适合"样板模式 + 廉价模型照做"的开发方式，减少 AI 犯错概率。

---

### 3. 生态成熟度

**TypeScript + NestJS**
- ✅ **ORM**: Prisma（类型安全、迁移管理优秀）或 TypeORM（装饰器实体）
- ✅ **认证**: @nestjs/passport + JWT 生态成熟
- ✅ **任务调度**: @nestjs/schedule（基于 node-cron）
- ✅ **测试**: Jest 深度集成，单元测试和 E2E 测试框架完善
- ✅ **验证**: class-validator + class-transformer（装饰器验证）
- ✅ **文档**: @nestjs/swagger 自动生成 OpenAPI 3.0
- ⚠️ 异步任务队列需额外引入 Bull（Redis）

**Python + FastAPI**
- ✅ **ORM**: SQLAlchemy（成熟但类型推导弱）或 Tortoise ORM（异步）
- ✅ **认证**: FastAPI-Users、authlib 等，但需手动组装
- ✅ **任务调度**: APScheduler 或 Celery（重量级）
- ✅ **测试**: pytest 强大，但异步测试配置相对繁琐
- ✅ **验证**: Pydantic 强大且简洁
- ✅ **文档**: 自动生成 OpenAPI 3.0（原生支持）
- ⚠️ 异步生态虽完善，但库的异步支持参差不齐

**结论**: NestJS 提供开箱即用的集成解决方案，FastAPI 需要更多选型和组装工作。对于 AI 协作开发，预集成方案减少决策点。

---

### 4. PostgreSQL 集成质量

**TypeScript + Prisma**
- ✅ Prisma Schema 清晰，迁移管理优秀（`prisma migrate`）
- ✅ 类型生成自动且准确，与 PostgreSQL 特性（JSON、数组、枚举）完美映射
- ✅ 查询构建器类型安全，复杂查询易读
- ⚠️ 原生 SQL 支持较弱，复杂查询需用 `$queryRaw`

**TypeScript + TypeORM**
- ✅ 装饰器实体与 NestJS 风格一致
- ✅ 支持原生 SQL 和查询构建器
- ⚠️ 迁移管理不如 Prisma 直观
- ⚠️ 类型推导偶尔不准确

**Python + SQLAlchemy**
- ✅ 成熟稳定，支持复杂查询和原生 SQL
- ✅ PostgreSQL 特性支持全面
- ⚠️ 类型提示需手动维护，与 Pydantic 的集成不如 Prisma 无缝
- ⚠️ 迁移工具 Alembic 学习曲线较陡

**结论**: Prisma 在类型安全和迁移管理上领先，适合本项目"强类型 + AI 协作"的需求。

---

### 5. 小团队维护成本

**TypeScript + NestJS**
- ✅ 前后端同一语言，减少上下文切换
- ✅ 框架约束强，代码风格一致性高，便于后期维护
- ✅ 单一 package.json 管理依赖
- ⚠️ Node.js 内存占用相对较高
- ⚠️ 装饰器和依赖注入初学曲线稍陡（但 AI 可弥补）

**Python + FastAPI**
- ✅ Python 语法简洁，上手快
- ✅ 适合数据处理和脚本任务（若未来有数据分析需求）
- ⚠️ 前后端分离需维护两套类型定义
- ⚠️ 异步编程（async/await）容易引入阻塞 I/O 的坑
- ⚠️ 依赖管理（pip/poetry）相比 npm 稍显混乱

**结论**: 对于产品负责人通过 AI 开发的场景，TypeScript 全栈减少认知负担，NestJS 的强约束降低维护成本。

---

## 最终推荐

**选择 TypeScript + NestJS + Prisma + PostgreSQL**

### 核心理由
1. **前后端类型共享**：DTO、Entity、API 响应类型可直接复用，减少 50% 的类型定义工作
2. **强制模块化架构**：NestJS 的 Module 系统天然适合"样板模块 + 廉价模型复制"的开发模式
3. **AI 协作友好**：装饰器清晰标记意图，AI 模型识别率高，生成代码一致性强
4. **Prisma 优势**：类型安全查询、迁移管理优秀、与 PostgreSQL 特性完美集成
5. **生态完整**：认证、验证、任务调度、测试、文档生成均有官方集成方案

### 技术栈明细
- **框架**: NestJS 10.x
- **语言**: TypeScript 5.x
- **ORM**: Prisma 5.x
- **数据库**: PostgreSQL 16
- **验证**: class-validator + class-transformer
- **文档**: @nestjs/swagger（OpenAPI 3.0）
- **测试**: Jest + Supertest
- **任务调度**: @nestjs/schedule
- **认证**: @nestjs/passport + JWT

### FastAPI 何时更合适？
如果项目满足以下条件，FastAPI 会是更好的选择：
- 团队已有 Python 生态积累（数据科学、ML 模型）
- 需要与现有 Python 服务集成
- 后端独立开发，前端由其他团队负责
- 追求极致的接口响应性能（异步 I/O 密集场景）

但本项目是 **单人通过 AI 全栈开发**，TypeScript 全栈 + 强约束架构的优势明显大于 Python 的灵活性。

---

## 后果

### 正面
- 前后端工程师只需掌握一门语言
- 类型错误在编译时发现，减少运行时故障
- 模块边界清晰，廉价模型按样板实现时不易出错
- Prisma 迁移管理降低数据库变更风险

### 负面
- Node.js 单线程模型在 CPU 密集任务上性能较弱（但本项目无此需求）
- 装饰器语法对不熟悉 TypeScript 的开发者有学习成本（通过 AI 辅助可缓解）
- 依赖 npm 生态，某些包质量参差不齐（需在 AGENTS.md 中规定可信依赖清单）

---

## 依赖版本锁定策略
为保证 AI 生成代码的一致性和构建稳定性，采用以下策略：
- 使用 `package-lock.json` 锁定依赖版本
- 关键依赖使用精确版本号（如 `"prisma": "5.7.0"`）
- 每月第一周集中进行依赖更新和测试
- CI 中启用依赖安全扫描（npm audit）
