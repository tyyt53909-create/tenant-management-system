# ADR-002: 多楼栋数据模型设计

## 状态
已接受 (2026-10-11)

## 背景
第一版为单楼栋场景，但需要预留未来扩展到多楼栋/多房东的能力。用户要求采用"方案B的轻量版"：设计 building(楼栋) 实体，第一版只有一条数据，核心业务表用非空 building_id 外键，权限按 building 范围过滤。暂不建模 landlord/organization。

## 方案对比

### 方案A：可空字段预留（❌ 已否决）
```prisma
model Room {
  id          String   @id
  buildingId  String?  // 可空，第一版不填
  // ...
}
```
**优点**: 第一版代码最简单  
**缺点**: 
- 可空外键导致数据完整性弱
- 查询时需处理 NULL 判断，易出错
- 二期迁移需修改所有历史数据

### 方案B：完整建模多楼栋（❌ 过度设计）
```prisma
model Organization {
  id        String     @id
  buildings Building[]
}

model Building {
  id             String       @id
  organizationId String
  organization   Organization @relation(...)
  rooms          Room[]
}
```
**优点**: 二期无需重构  
**缺点**: 第一版引入不必要的复杂度，权限逻辑需处理组织和楼栋两层

### 方案C：完全不预留（❌ 二期成本高）
第一版不设计 building 实体，所有数据挂在全局。  
**缺点**: 二期需大规模重构数据库和权限系统

---

## 决策：方案B的轻量版（✅ 已采纳）

### 设计原则
1. **建立 Building 实体**，第一版创建一条默认数据（如 `id: "default-building"`）
2. **核心业务表使用非空 `building_id` 外键**，保证数据完整性
3. **权限按 building 范围过滤**，第一版硬编码单楼栋，二期改为动态多楼栋
4. **暂不建模 Landlord/Organization**，在 Building 上预留可空的 `metadata` JSON 字段存储扩展信息

### 数据模型

```prisma
model Building {
  id          String   @id @default(cuid())
  name        String   // "XX号楼"
  address     String?  // 详细地址
  floors      Int      // 楼层数
  metadata    Json?    // 扩展信息（预留）
  isActive    Boolean  @default(true)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  // 关联
  rooms       Room[]
  publicAreas PublicArea[]
  contracts   Contract[]
  // ... 其他业务实体
}

model Room {
  id         String   @id @default(cuid())
  buildingId String   // 非空外键
  building   Building @relation(fields: [buildingId], references: [id])
  floor      Int
  roomNumber String
  // ...
  
  @@unique([buildingId, floor, roomNumber]) // 同一楼栋内房号唯一
}

model Contract {
  id         String   @id @default(cuid())
  buildingId String   // 非空外键
  building   Building @relation(fields: [buildingId], references: [id])
  roomId     String
  room       Room     @relation(...)
  // ...
}
```

### 第一版实现

#### 1. 数据初始化
在数据库迁移或应用启动时，自动创建默认楼栋：

```typescript
// prisma/seed.ts
async function seedDefaultBuilding() {
  await prisma.building.upsert({
    where: { id: 'default-building' },
    update: {},
    create: {
      id: 'default-building',
      name: '默认楼栋',
      floors: 7,
      isActive: true,
    },
  });
}
```

#### 2. 权限过滤（第一版硬编码）
```typescript
// auth/guards/building.guard.ts
export class BuildingGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    // 第一版：所有用户默认访问 default-building
    request.buildingId = 'default-building';
    return true;
  }
}
```

#### 3. 服务层自动注入 buildingId
```typescript
// rooms/rooms.service.ts
@Injectable()
export class RoomsService {
  async findAll(buildingId: string) {
    return this.prisma.room.findMany({
      where: { buildingId }, // 第一版始终为 'default-building'
    });
  }
}
```

## 第二阶段扩展路径

### 扩展 1：多楼栋（单房东）
1. **数据层**：Building 表已存在，新增更多楼栋记录
2. **权限层**：修改 `BuildingGuard`，从用户关联的楼栋列表中过滤
3. **UI层**：新增楼栋选择器

**改动量**: 小（核心数据模型无需变更）

### 扩展 2：多房东（需新增实体）
```prisma
model Landlord {
  id        String     @id @default(cuid())
  name      String
  phone     String
  email     String?
  buildings Building[] // 一个房东管理多个楼栋
}

model Building {
  id         String    @id
  landlordId String    // 新增外键
  landlord   Landlord  @relation(fields: [landlordId], references: [id])
  // ... 其他字段不变
}

model User {
  id          String   @id
  landlordId  String?  // 管理者关联到房东
  landlord    Landlord? @relation(...)
  // ...
}
```

**权限变更**：
- 管理者只能访问自己 `landlordId` 下的楼栋
- 租客权限不变（仅访问自己的合同和房间）

**改动量**: 中等（新增实体和关联，权限过滤逻辑升级）

### 扩展 3：集团/组织层级
```prisma
model Organization {
  id        String     @id
  name      String
  landlords Landlord[]
}

model Landlord {
  id             String       @id
  organizationId String
  organization   Organization @relation(...)
  // ...
}
```

**权限变更**：三层权限树（组织 → 房东 → 楼栋）

**改动量**: 大（需重构权限系统为树形结构）

## 预留策略

### metadata JSON 字段用途
在 Building 表中预留 `metadata` JSON 字段，第一版可存储：
```json
{
  "landlordName": "张三",  // 房东姓名（非规范化，便于第一版快速展示）
  "contactPhone": "138****1234",
  "notes": "自建楼，共7层"
}
```

第二阶段迁移时：
1. 新建 Landlord 表
2. 从 `metadata` 中提取房东信息生成 Landlord 记录
3. 建立 Building → Landlord 外键关联
4. 清空或废弃 metadata 中的房东字段

### 优势
- **渐进式复杂度**：第一版不引入多余实体，保持简单
- **数据完整性**：非空外键保证关联有效，无需处理 NULL
- **扩展灵活**：二期可无缝添加 Landlord 或 Organization，核心业务逻辑（Room、Contract、Billing）无需修改
- **权限可测试**：第一版权限虽硬编码，但接口已按 buildingId 过滤，二期只需替换 Guard 实现

---

## 后果

### 正面
- 第一版代码简洁（单楼栋硬编码），但数据模型为多楼栋准备就绪
- 所有业务查询和权限过滤统一按 buildingId 处理，二期扩展无需重构核心逻辑
- 数据库约束（非空外键、唯一索引）保证数据质量

### 负面
- 第一版需维护一条"虚拟"的默认楼栋数据
- Building 表在第一版只有一条记录，但所有业务表都需关联它（增加少量存储和查询开销，可忽略）

### 风险缓解
- **误删默认楼栋**：数据库级外键约束会阻止删除（有关联数据时）
- **硬编码 ID 冲突**：使用 UUID 或明确的字符串 ID（如 `default-building`），避免自增 ID 冲突

---

## 验收标准
1. 所有核心业务表（Room、Contract、Billing、MaintenanceRequest 等）都有非空 `buildingId` 外键
2. 数据库迁移脚本包含默认楼栋的创建
3. 权限 Guard 正确注入 `buildingId` 到请求上下文
4. 所有查询接口都按 `buildingId` 过滤
5. ADR 清晰描述第二阶段如何扩展到多楼栋和多房东
