# 租客帳號能力開關 — 實施計劃

> 狀態: 待確認後開工  
> 日期: 2026-10-15  
> 建議任務: T173（下一號；`tasks/` 現有最大已建檔為 T171，交接記錄已用到 T172）  
> 建議分支: `feature/T173-tenant-capabilities`  
> 檔位: 強（權限邊界、資料隔離、審計）  
> 範圍: 只管理已註冊的 `TENANT` 普通帳號。不提升角色，不開放管理者能力。

---

## 1. 決定

後台要能對某個租客的登入帳號：禁用登入、恢復登入、單獨屏蔽或恢復某幾項租客功能。

不做完整 RBAC。`docs/03-权限矩阵.md` §7.2 的 Permission / RolePermission 是留給「唯讀管理者」這類後台角色的，第一版明確不實現。本功能是租客角色之上的個人例外，不是第二套角色。

三層必須分開，不能用一個開關代替：

| 層 | 欄位 / 資料 | 含義 | 現況 |
|---|---|---|---|
| 檔案 | `Tenant.isActive` | 這個人還算不算在租 | 後台已有啟用 / 停用 |
| 登入帳號 | `User.isActive` | 能不能登入、舊 token 是否立即失效 | 登入與 `JwtStrategy` 已攔截；後台沒有入口 |
| 功能權限 | 新建覆蓋表 | 登入之後能用哪些租客功能 | 沒有，全靠 `User.role` 寫死 |

`Tenant.tags` 繼續只做篩選，不參與權限。文件已寫明標籤不影響權限判斷。

---

## 2. 不做

- 不把租客改成 `ADMIN` 或 `CLEANER`，這個畫面沒有改角色。
- 不把確認收款、改房態、錄入水電、看別人的帳單、看證件、看審計日誌放進可勾選清單。
- 不把能力清單寫進 JWT。現有 payload 只有 `sub`、`role`、`buildingId`、`tokenType`。管理員一改權限，舊 token 仍要在下一次請求被擋住。
- 不在本計劃裡新做「自助抄表」「租客改手機號」。權限矩陣裡有、程式裡還沒有的接口，不借這次順便做出來。
- 不對尚未註冊的檔案預存權限。沒有 `User` 就沒有可管理的帳號。
- 不改 `Tenant.isActive` 的現有含義，避免和禁用登入混在一起。

資料範圍維持現狀：租客只能看自己的 `tenantId`。能力開關不能擴大資料範圍。`JwtStrategy` 對沒有租客檔案的 `TENANT` 直接拒絕，這條安全紅線不動。

## 3. 能力清單

清單寫在程式裡，不做成後台可隨意新增的權限表。資料庫只存例外。沒有例外的帳號，行為與今天完全相同。

同一項若同時出現允許和屏蔽，屏蔽贏。第一版介面只產生屏蔽，不產生允許。允許留給以後「預設關閉、可單獨打開」的項，本版不開放勾選。

### 3.1 第一版可屏蔽（都有現成租客接口）

| 代碼 | 顯示名 | 預設 | 要攔截的接口 |
|---|---|---|---|
| `tenant.contract.read` | 查看自己的合同 | 允許 | `GET /contracts/my`、`GET /contracts/:id`、`GET /contracts/:id/attachments`、`GET /contracts/:id/attachments/:attachmentId/file` |
| `tenant.bill.read` | 查看自己的帳單與收據 | 允許 | `GET /bills/my`、`GET /bills/:id`、`GET /bills/:id/receipt` |
| `tenant.prepay.read` | 查看自己的預付帳戶與流水 | 允許 | `GET /prepay-accounts/my`、`GET /prepay-accounts/transactions` |
| `tenant.maintenance.read` | 查看自己的報修 | 允許 | `GET /maintenance/my`、`GET /maintenance/:id` |
| `tenant.maintenance.create` | 提交報修 | 允許 | `POST /maintenance` |
| `tenant.checkout.read` | 查看自己的退租結算 | 允許 | `GET /checkout`、`GET /checkout/:id`、`GET /checkout/:id/voucher` |

以上接口今天都標了 `TENANT`（或 `TENANT` + `ADMIN`）。守衛只在 `role === TENANT` 時檢查能力。管理者走原有 `RolesGuard`，不受這張表影響。

`GET /tenants/:id` 雖允許租客，但是看自己的檔案，不納入可屏蔽項。個人中心必須還能打開。

### 3.2 不可屏蔽

| 代碼 | 原因 |
|---|---|
| `tenant.notification.read` | 停用通知會讓催租、報修進度送不到人。通知接口已按 `userId` 隔離，維持現狀 |
| 登入、`GET /auth/me`、重新整理 token | 禁用登入走 `User.isActive`，不走能力表 |

### 3.3 矩陣有、程式沒有，本版不建接口

這些只記在計劃裡，不進第一版清單，避免做出新功能：

- 租客改緊急聯絡人 / 信箱：`PATCH /tenants/:id` 目前只有 `ADMIN`
- 租客確認完工、取消已提交工單：`PATCH /maintenance/:id` 目前只有 `ADMIN`
- 租客看自己房間的水電：`meters` 控制器全部是 `ADMIN`
- 自助抄表、租客改手機號：沒有接口

若以後要做，先加接口和測試，再把代碼加進清單，預設允許或預設關閉分開寫。不要在權限頁用自由字串開後門。

## 4. 資料模型

新增一張表，掛在 `User`，不掛在 `Tenant`。遷移必須單獨、串行，不能和其他改 `schema.prisma` 的任務並行。

```prisma
enum CapabilityEffect {
  ALLOW
  DENY
}

model UserCapabilityOverride {
  id         String           @id @default(cuid())
  userId     String
  user       User             @relation(fields: [userId], references: [id], onDelete: Cascade)
  capability String
  effect     CapabilityEffect
  reason     String?
  grantedBy  String
  createdAt  DateTime         @default(now())
  updatedAt  DateTime         @updatedAt

  @@unique([userId, capability])
  @@index([userId])
  @@map("user_capability_overrides")
}
```

`User` 增加反向關聯 `capabilityOverrides UserCapabilityOverride[]`。

第一版不建 `expiresAt`。臨時屏蔽放到第二期，避免過期判斷散落在守衛和介面。

`capability` 不設資料庫外鍵。合法值以程式清單為準，寫入時拒絕未知代碼。

## 5. 生效規則

```
若 role 不是 TENANT：不看這張表
若能力不在清單：拒絕（未知代碼不能當放行）
若存在未過期的 DENY：拒絕
若存在 ALLOW：允許
否則：用清單預設（第一版全部是允許）
```

第一版沒有到期時間，所以上面的「未過期」先不實現。規則寫成這樣，是為了第二期加到期時不用改判斷順序。

屏蔽只影響租客自己呼叫。管理者代查、代建報修不受影響。

## 6. 後端

建議新模組 `backend/src/modules/tenant-capabilities/`，不要把判斷散進各個 service。

### 6.1 清單與服務

- `tenant-capability.catalog.ts`：代碼、顯示名、預設、分組。這是唯一註冊處。
- `tenant-capability.service.ts`：
  - `effective(userId)`：回傳目前生效的代碼列表，給 `GET /auth/me` 和小程序用。
  - `assert(user, code)`：租客且未生效則丟 `ForbiddenException`。
  - `replace(userId, denies, actorId)`：整批替換該用戶的 `DENY` 記錄。傳空陣列等於恢復全部預設。
- 未知代碼、重複代碼、清單外代碼：400，不寫庫。

### 6.2 守衛

沿用現有裝飾器風格（`roles.decorator.ts` / `roles.guard.ts`）：

- `@RequireCapability('tenant.maintenance.create')`
- `CapabilityGuard` 放在 `RolesGuard` 之後。
- 非租客直接通過。
- 租客不通過時回 403，訊息固定、可被前端辨識，例如 `CAPABILITY_DENIED`。不要只回「權限不足」，否則和小程序現有的角色錯誤混在一起。

每個租客接口顯式標能力，不要用一個全域守衛去猜路徑。漏標的接口維持今天的行為，測試要列出「已標 / 未標」，避免悄悄漏掉 `POST /maintenance`。

### 6.3 帳號接口

掛在現有租客資源上，管理者專用。實作時先看 `TenantsController.findOne` 怎麼確認租客存在，沿用同一套 404。

| 方法 | 路徑 | 作用 |
|---|---|---|
| `GET` | `/tenants/:id/account` | 帳號狀態。沒有 `userId` 時回 `{ status: "UNREGISTERED" }`，不要 500 |
| `PATCH` | `/tenants/:id/account` | `{ isActive: boolean }`。只改 `User.isActive`，不改 `Tenant.isActive` |
| `GET` | `/tenants/:id/capabilities` | 清單 + 目前覆蓋 + 生效結果，供後台渲染開關 |
| `PUT` | `/tenants/:id/capabilities` | `{ denied: string[], reasons?: Record<string, string> }`。整批替換 DENY |

`PATCH` / `PUT` 在沒有關聯 `User` 時回 409，訊息說明尚未註冊。不自動建帳號。

禁用登入不需要改 `JwtStrategy`。它已經在每次請求查 `isActive`，禁用後舊 access token 會立刻失效。恢復登入同理。

### 6.4 `GET /auth/me`

在現有回傳上增加：

```json
{
  "capabilities": ["tenant.contract.read", "tenant.bill.read"]
}
```

只回生效代碼，不回原因、不回其他租客的覆蓋。非租客回空陣列或省略，兩種擇一，實作時固定一種並寫進接口規範。

### 6.5 審計

用現有 `AuditLogService.log`。`changes` 必填。

| action | 時機 |
|---|---|
| `DISABLE_TENANT_ACCOUNT` | `isActive` true → false |
| `ENABLE_TENANT_ACCOUNT` | false → true |
| `UPDATE_TENANT_CAPABILITIES` | 覆蓋集合有變化 |

`entityType` 用 `User`，`entityId` 用被改的 userId。`changes` 記 before / after，以及操作者。沒有變化不寫日誌。

ip、userAgent 沿用現有審計呼叫方式。若現有呼叫點沒有從 request 帶入，本任務補上，不要寫空字串湊過去。

### 6.6 測試

放在新模組的 `*.spec.ts`，至少覆蓋：

- 無覆蓋時，租客呼叫 `POST /maintenance` 與今天一樣成功。
- 屏蔽 `tenant.maintenance.create` 後，同一租客 403，且錯誤可辨識為 `CAPABILITY_DENIED`。
- 同一屏蔽不影響管理者代建，也不影響該租客仍被允許的 `GET /bills/my`。
- 屏蔽不能讓租客讀到別人的資料；既有的 tenantId 隔離測試保持通過。
- 未知能力代碼 400，不落庫。
- 禁用帳號後，舊 access token 被 `JwtStrategy` 拒絕；恢復後可再登入。
- 未註冊檔案不能寫能力、不能改登入狀態。
- 每次實際變更都有一筆審計；重複提交相同 DENY 集合不新增審計。

後端命令在 `backend/` 執行：`npm test`、`npm run lint`。改 schema 後要有遷移，不手改已套用的 migration。

## 7. 管理後台

不加獨立選單。入口在租客檔案抽屜。

現有頁籤在 `frontend-admin/src/utils/resourceDetail.ts`：基本資料、租賃關聯、操作記錄。新增第四個：**登入帳號**。

頁籤內容：

- 未註冊：說明註冊後才能設定，開關全部不可用。
- 已註冊：信箱或手機、最後登入時間、登入狀態。
- 主操作：禁用登入 / 恢復登入。文案寫明「立即無法登入，不影響檔案啟用狀態」。
- 功能開關按組顯示：合同、帳單、預付、報修、退租。
- 每一項顯示「預設允許」或「已屏蔽」。屏蔽可填原因，原因可選。
- 不顯示管理者能力，也不顯示通知開關。
- 儲存失敗要能重試，沿用現有詳情抽屜的錯誤狀態，不要只彈一個消失的訊息。

列表頁 `frontend-admin/src/views/tenants/index.vue` 不必改欄位。檔案啟用和登入禁用不是同一列，避免在列表上再加一個容易點錯的開關。登入狀態只在抽屜裡看。

## 8. 小程序

伺服器攔截是準的。客戶端只負責少讓人點到必定失敗的入口。

`pages.json` 的 tabBar 是靜態的，第一版不改成自訂 tabBar。帳單、報修兩個 tab 仍在。對應能力被屏蔽時，頁面內顯示說明（例如「此功能已被暫停，如有需要請聯絡管理處」），並隱藏提交按鈕。不要只藏按鈕卻讓接口還能打出去。

首頁和個人中心裡，通往合同、預付、退租的入口，依 `GET /auth/me` 的 `capabilities` 隱藏。`/auth/me` 失敗時不要當成「全部允許」把入口放出來；顯示載入失敗和重試。

通知頁不隱藏。

## 10. 驗收

- 未改過權限的租客，合同、帳單、預付、報修、退租與今天一致。
- 只屏蔽提交報修時，該租客 `POST /maintenance` 為 403，查看自己的工單仍可用，其他租客不受影響。
- 禁用登入後，該帳號立即不能用舊 token；檔案頁的啟用狀態不變。
- 恢復登入、清空屏蔽後，行為回到預設。
- 管理者帳號的全部接口不因這張表改變。
- 保潔帳號不能呼叫這四個管理接口。
- 審計日誌能看出誰在什麼時候禁用了誰、屏蔽了哪幾項。
- 後台不能勾到清單以外的能力。
