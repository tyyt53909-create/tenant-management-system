# 多实例运行约束（OPS-06 / T279）

## 1. 必须共享的状态

| 状态 | 存放 | 多实例要求 |
|---|---|---|
| 登录会话 / refresh 轮换 | Redis | 所有实例共用同一 Redis DB |
| OTP / 登录失败计数 / 限流 | Redis | 同上 |
| 后台任务队列 | Redis（BullMQ） | Web/Worker 共用 `QUEUE_PREFIX` 与 DB |
| 业务数据 | PostgreSQL | 共用同一库 |
| 文件 | 对象存储（S3/OSS） | `MULTI_INSTANCE=true` 时强制 `STORAGE_DRIVER=s3` |
| 定时任务互斥 | PostgreSQL advisory lock | 已实现 |

## 2. 启动约束

- `MULTI_INSTANCE=true` 且 `STORAGE_DRIVER!=s3`：生产/预发拒绝启动；开发只警告。
- 生产 Redis 不可用时拒绝启动（OPS-01）；不会退化成内存会话。
- `INSTANCE_ID` 可选，仅用于日志排查。

## 3. Redis 连接语义

`RedisService.connect()` 并发调用共享同一个连接 Promise。此前用 `started` 标志提前返回，后到的 `REFRESH_STORE`/OTP 工厂可能在 Redis 未 ready 时退化为内存实现，导致：

- 实例 A 登录、实例 B 刷新令牌失败；
- 多实例下限流/OTP 计数不共享。

修复后所有调用等待同一个连接结果；失败后清空 Promise，允许后续重试（生产仍拒绝启动）。

## 4. readiness

- `STORAGE_DRIVER=s3` 时不再检查本地 `UPLOAD_DIR`，避免对象存储部署因只读根文件系统被判 down。
- 数据库、Redis 任一不可用仍返回 503。

## 5. 验证

`backend/test/integration/multi-instance.int-spec.ts`：

1. 实例 A 登录的 access token 在实例 B 访问 `/tenants` 返回 200；
2. 实例 A 的 refresh token 在实例 B `/auth/refresh` 可轮换（返回新 access token）。

## 6. 已知边界

- 本地文件存储仍支持单实例部署；多实例必须迁移对象存储。
- 未做容器级双实例压测，性能/SLO 见 OPS-09。
- 队列模式下 cron 只入队；多实例 Web 同 jobId 幂等，最终仍由咨询锁保证只执行一次。
