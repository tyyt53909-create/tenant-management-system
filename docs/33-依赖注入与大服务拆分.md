# 依赖注入清理与大服务拆分（QLT-02 / T288）

## 1. 问题：静默降级（ISS-38）

改造前有 **42 处** `@Optional()`、其中 **19 处** 伴随 `?? new X()`。这类写法的问题不是「不优雅」，
而是**失败模式错了**：

| 场景 | 改造前行为 | 后果 |
|---|---|---|
| `AuthModule` 漏注册 `OTP_STORE` | `?? new MemoryOtpStore()` | 多实例下 A 发的码 B 验证不了，日志无异常 |
| `BillsModule` 漏注册 `PAYMENT_PROVIDER` | `?? new OfflinePaymentProvider()` | 生产漏配支付通道 → 静默走线下，账对不上 |
| `MeterPriceService` 未注入 `BusinessClock` | `new BusinessClock(new ConfigService())` | 绕过 `BUSINESS_TIMEZONE`，月末结算可能落到错误业务日 |
| `MetersService` 未注入适配器 | `new ManualMeterAdapter()` | 模拟器/设备模式失效，退回手工读数 |
| `NotificationsService` 未注入 dispatcher | `createDefault(prisma)` | 测试替身失效，无法替换渠道实现 |

共同点：**容器装配错误被推迟成业务运行时的诡异现象**，而且测试因为走的是同一条降级路径，往往也发现不了。

## 2. 改造原则

> 关键依赖缺失时，进程在**启动阶段**就失败；只有「缺了它功能依然正确」的依赖才允许可选。

### 2.1 改为必填（本轮）

| 模块 | 依赖 | 现在由谁提供 |
|---|---|---|
| `BillsService` | `BillPaymentService` / `BillLateFeeService` / `BillReceiptService` | `BillsModule` providers |
| `BillPaymentService` | `PAYMENT_PROVIDER` / `BusinessClock` | `BillsModule` 工厂 + 全局 `BusinessClockModule` |
| `MetersService` | 6 个子服务 + `METER_ADAPTER` + `MeterPriceService` | `MetersModule` providers |
| `MeterService` | `METER_ADAPTER` / `MeterPriceService` | `MetersModule` 工厂 |
| `MeterBillingService` | `BusinessClock` / `MeterPriceService` | 容器 |
| `MeterReadingService` | `MeterBillingService` / `MeterPriceService` | 容器 |
| `MeterBatchReadingService` | 同上 | 容器 |
| `MeterUsageQueryService` | `BusinessClock` / `MeterPriceService` | 容器 |
| `MeterReconciliationService` | `MeterPriceService` | 容器 |
| `MeterPriceService` | `BusinessClock` | 全局模块 |
| `PublicUtilitiesService` | `MeterPriceService` | `PublicUtilitiesModule`（已 import `MetersModule`） |
| `EmailOtpService` | `OTP_STORE` | `AuthModule` 工厂（Redis / 内存二选一） |
| `AuthService` | `LOGIN_ATTEMPT_STORE` / `FederatedAuthService` | `AuthModule` providers |
| `NotificationsService` | `NotificationDispatcher` | `NotificationsModule` 工厂 |
| `AnnouncementsService` | `NotificationsService` | `AnnouncementsModule` |

`PAYMENT_PROVIDER` 之前**没有任何模块注册**（只靠 `?? new OfflinePaymentProvider()` 兜底），
本轮补上显式 provider —— 接入微信支付时只改这一处工厂。

### 2.2 保留可选（有明确理由）

| 位置 | 原因 |
|---|---|
| `SchedulerService` 的 metrics / alerts / config / jobs | 未配置时定时任务仍同步执行，属于部署模式差异 |
| `SchedulerService` 的 dailyJobs / monthlyBills | 未注入时构造只用 prisma 的默认实现 |
| `NotificationsService` 的 gateway | Worker / 单测进程没有 WebSocket server |
| `JwtAuthService` 的 `REFRESH_STORE` | 单测可直接构造内存实现，不依赖 Redis |
| `TenantCapabilityService` 的 `JwtAuthService` | 仅用于主动吊销会话，缺省不影响能力判定 |
| `CapabilityGuard` 的 `TenantCapabilityService` | 只有租客端路由使用 |
| `MetersSimulatorService` 的 anomalyRunner | 调试入口，仅在 `METER_MODE=simulator` 时使用 |

## 3. 大服务拆分：RoomsService

`rooms.service.ts` 603 行，里面混着三类完全不同的东西：照片落库规则、房态状态机、CRUD。
拆出两个文件：

### 3.1 `room-photos.ts`

| 导出 | 职责 |
|---|---|
| `photoKey(url)` | 只接受 `/api/files/...` 或 `/api/public/files/...`，拒绝站外地址与路径穿越（ISS-06 回归） |
| `collectPhotoKeys(photos)` | 主图 + 缩略图去重 |
| `buildRoomPhotoRows(photos)` | 校验 20 张上限，按数组顺序写 `sortOrder` |
| `bindPhotoAssets(db, photos, roomId)` | 确认资产经上传接口登记，绑定 `ROOM_PHOTO/PUBLIC/ROOM` |

### 3.2 `room-transitions.ts`

| 导出 | 职责 |
|---|---|
| `ALLOWED_ROOM_TRANSITIONS` | docs/04 §1.3 的流转表（唯一来源） |
| `isTransitionAllowed(from, to)` | 纯判断，同状态幂等 |
| `requiredPreconditions(from, to)` | 返回需要查库的前置条件列表 |
| `assertTransitionTable` / `assertPreconditionMet` | 抛 400 / `ROOM_NOT_AVAILABLE` |

`RoomsService` 只剩「查库 + 编排」：`hasPrecondition()` 按 kind 分派一次查询，
不再有 4 段几乎相同的 `if` 块。行数 603 → 540。

## 4. 防回归：静态扫描

`backend/src/common/dependency-hygiene.spec.ts`：

1. 扫描 `src/**/*.ts`（排除 spec），列出所有 `@Optional()` 与 `?? new X()` 的文件；
2. 与**白名单**逐条比对 —— 多一处失败，少一处也失败（防止清单腐烂）；
3. 每个白名单条目必须写明原因（长度 > 8 字）；
4. 关键模块（bills / auth / meters / public-utilities / announcements）硬性要求：
   `@Optional()` 与 `?? new` 数量必须为 0。

扫描前先剥离注释，避免文档里提到 `@Optional()` 造成误报；`?? new Date()` / `?? new Set()`
这类值构造不算依赖降级，排除。

## 5. 测试装配

依赖必填后，测试必须显式提供。新增 `meters/meter-test.providers.ts`：

```ts
export function testClock(): BusinessClock
export function testPriceService(prisma): MeterPriceService
export function meterTestProviders(prisma)  // 可直接展开进 providers
```

各 spec 统一用它构造，而不是各自 `new BusinessClock(new ConfigService())` —— 那正是本任务要消灭的模式。

## 6. 已知边界

- 未拆 `AuthService`（497 行）/ `TenantsService`（533 行）/ `MetersService` 的门面转发本身；
  本轮先解决「依赖静默降级」，进一步拆分需要先补对应集成用例。
- `MetersService` 仍是 7 个方法的编排门面，可考虑按「表管理 / 读数 / 结算」再拆，但会改动
  controller 与多个 spec，留待 M3。
- 白名单是人工维护的；新增可选依赖需要同时改代码与测试，这是有意设计的摩擦。
