# 公告与定向消息（COM-04 / T284）

## 1. 为什么需要独立公告表

通知表（`notifications`）是「一条通知属于一个用户」的投递结果，不带「这次发给谁、为什么发给这些人」。
公告需要回答：谁发的、发给哪一类人、有没有重发过、实际送达多少人。因此新建 `announcements` 保存**意图**，
发布时再解析成具体的通知记录。

## 2. 数据

| 字段 | 说明 |
|---|---|
| title / body | 标题 ≤200 字、正文 ≤5000 字 |
| priority | `NORMAL` / `URGENT`；`URGENT` 同时走邮件渠道（通知中心既有规则） |
| status | `DRAFT` → `PUBLISHED` → `ARCHIVED` |
| audience | `ALL_TENANTS` / `BUILDING` / `TAGS` / `TENANTS` |
| targetIds | `TEXT[]`；按 audience 解释为楼栋 / 标签 / 租客 ID |
| publishedAt | 首次发布时间；重发不覆盖 |
| recipientCount | 最近一次发布解析出的接收人数 |

## 3. 受众解析

| audience | 解析规则 |
|---|---|
| ALL_TENANTS | `Tenant.isActive = true` 且已有登录账号（`userId` 非空） |
| BUILDING | 该楼栋 `status = ACTIVE` 的合同 → 去重后的租客 |
| TAGS | `tenant_tags` 中带这些标签的租客 |
| TENANTS | 直接指定的租客 |

**没有登录账号的租客不计入**：站内通知需要 `userId`，把「没有账号的人」算进接收数会造成
「显示已发送 20 人、实际只到 12 人」的假象。需要在未开通账号的租客处触达，应走短信/纸质通知（后续任务）。

## 4. 投递与幂等

- 发布时逐个调用 `NotificationsService.create`，因此自动获得站内通知 + WebSocket 实时推送。
- 去重键 `ANNOUNCEMENT:{announcementId}:{userId}`：重发不会给同一人再发一条。
- 单个用户投递失败不影响其他人；失败明细写入响应 `errors`，并以 `failed` 计数返回。
- 投递不在数据库事务内：外部渠道（邮件）不应拖住数据库事务。

## 5. 生命周期约束

| 动作 | 允许状态 | 原因 |
|---|---|---|
| 编辑 | 仅 DRAFT | 已发布内容已进入租客通知箱，改正文会让「通知里的内容」与「公告内容」不一致 |
| 发布 / 重发 | DRAFT、PUBLISHED | 重发用于补发新增租客（去重键保证不重复打扰） |
| 归档 | 任意非归档 | 归档只影响列表，已送达通知不回收 |
| 删除 | 仅 DRAFT | 已发布公告是送达记录，不能硬删除 |

## 6. 权限

- 全部公告管理接口仅 `ADMIN`；`CLEANER` / `TENANT` 返回 403（路由快照已登记）。
- 租客不直接读公告表，只从通知中心接收；这样已读状态、未读计数与其它通知完全一致。

## 7. 已知边界

- 不支持定时发布（`publishAt` 字段保留但未接调度）；当前是人工点发布。
- 不支持富文本/附件，纯文本换行即可。
- 受众解析仍是「发布时刻快照」，发布后新增的租客不会自动收到；需要时手动重发。
- 没有公告已读统计（只统计送达人数），已读率需在通知维度统计。
