# T139: 房态状态机 + 乐观锁（样板完整性收口）

## 背景

`docs/04-状态机.md` §1 早已定义房间状态机（四态 × 三清洁态流转表 + 前置条件 + 乐观锁），但 rooms 样板从未实现：状态可任意改、`version` 字段建了不用、硬删除不设防。本任务按文档落地，补上最后一个「样板完整性」缺口。

---

## 任务范围

### 后端

1. **房态流转表落地**（`ALLOWED_ROOM_TRANSITIONS`，键值均为 `status+cleanStatus`）：
   - VACANT+CLEAN → RESERVED+CLEAN / MAINTENANCE+CLEAN
   - RESERVED+CLEAN → OCCUPIED+CLEAN
   - OCCUPIED+CLEAN → VACANT+PENDING_CLEAN / MAINTENANCE+CLEAN
   - MAINTENANCE+CLEAN → OCCUPIED+CLEAN / VACANT+PENDING_CLEAN
   - VACANT+PENDING_CLEAN → VACANT+CLEANING
   - VACANT+CLEANING → VACANT+CLEAN
2. **前置条件**（不满足 400，带明确提示）：
   - → RESERVED：需有 DRAFT 合同
   - RESERVED → OCCUPIED：合同起始日 ≤ 今日（DRAFT/ACTIVE）
   - → VACANT+PENDING_CLEAN：需有退租记录
   - → MAINTENANCE：需有报修工单
3. **新增 `PATCH /rooms/:id/status`**（ADMIN）：`{ status?, cleanStatus?, version }`，version 必填（乐观锁，冲突 409「房间状态已被其他用户修改，请刷新后重试」）
4. **通用更新 `PATCH /rooms/:id` 同样受状态机约束**（改 status/cleanStatus 走同一校验），version 可选（提供则冲突检查 409），每次成功更新 version 递增
5. **删除守护**：`DELETE /rooms/:id` 有关联数据（合同/水表/报修/退租/照片）→ 400
6. 修复发现的历史 Bug：前端提交 `monthlyRent/deposit`（DTO 不存在）导致**房源创建/编辑必 400**；`cleanStatus` 前端枚举值错误（NEEDS_CLEANING/IN_CLEANING）

### 前端

7. 房源页新增「房态」对话框（当前状态/版本展示 + 流转选择 + 乐观锁提交）
8. 编辑表单携带 `version`（冲突被拦截为 409 中文提示）；移除不存在的月租金/押金字段

### 测试

9. `rooms.service.spec.ts` 扩充：+13 例（合法/非法流转、四项前置条件、版本冲突 409、保洁流转、删除守护、update 乐观锁）
10. DTO 测试 +5 例（UpdateRoomStatusDto：version 必填、枚举、负数）

## 决策记录

- 保洁角色流转（CLEANING→CLEAN）v1 暂由 ADMIN 操作，与文档「管理者可代为操作」一致；保洁专属账号/UI 留待保洁功能任务
- `PATCH /:id` 的 version 为可选（向后兼容），`PATCH /:id/status` 必填（并发关键路径）
- 删除策略：非软删除，但有关系数据一律拒绝
- 前端月租金/押金字段移除：租金信息归属合同（Contract），房间表无此字段
