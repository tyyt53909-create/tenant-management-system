# T278：背景任务：BullMQ、Worker、死信队列（OPS-05）

## 背景

DEC-06 已拍板 BullMQ；当前定时任务与 Web 进程同生命周期（`@nestjs/schedule` 直接执行），重任务会占用请求线程，失败只能靠 `JobRun` 事后查。需要把「触发」与「执行」拆开：Web 只入队，独立 Worker 消费，失败可重试、可查看/重放。

## 范围

### 1. 队列与生产者

- 新增 `bullmq` 依赖与 `modules/jobs`：
  - `JobsQueueService`：懒创建 `Queue('scheduler')`，连接复用 `REDIS_URL` / HOST/PORT/PASSWORD/DB。
  - `enqueue(name, { dedupeKey })`：`jobId = scheduler:{name}:{dedupeKey}` 幂等；未启用 `QUEUE_ENABLED=true` 时返回 `null`。
- `SchedulerService` 的 cron 触发改为：
  - `QUEUE_ENABLED=true` → 入队（`trigger=QUEUE`），Web 不执行任务；
  - 未启用 → 维持现有同步执行（兼容单机/测试）。
- 手动 `POST /scheduler/:name/run` 保持同步执行，便于运维立即看结果。

### 2. Worker

- 新增 `src/worker.ts`：Nest application context（无 HTTP），启动 BullMQ `Worker('scheduler')`，调用 `SchedulerService.rerun(name,'QUEUE')`。
- `PROCESS_ROLE=worker` 时 Web cron 不执行（避免 Worker 里 `@nestjs/schedule` 重复触发）。
- 优雅关闭：SIGTERM/SIGINT → `worker.close()` → `app.close()`；并发 `QUEUE_CONCURRENCY`。
- 重试：`QUEUE_ATTEMPTS`（默认 3）+ 指数退避 `QUEUE_BACKOFF_MS`（默认 5000）。

### 3. 死信队列与运维接口

- 失败任务保留在 BullMQ failed 集合；ADMIN 接口：
  - `GET /jobs/failed?limit=`：id/name/data/failedReason/attemptsMade/timestamp。
  - `POST /jobs/failed/:id/retry`：重放。
  - `DELETE /jobs/failed/:id`：清理。
- 队列总览 `GET /jobs/stats`：waiting/active/completed/failed/delayed。

### 4. 配置、测试与文档

- 环境变量：`QUEUE_ENABLED`、`QUEUE_CONCURRENCY`、`QUEUE_ATTEMPTS`、`QUEUE_BACKOFF_MS`、`QUEUE_PREFIX`、`PROCESS_ROLE`；两套模板同步。
- 单元：未启用不建队列、jobId 幂等、失败列表/重试/清理、Worker 调用 run、cron 在 worker 角色直接返回。
- 集成（真实 Redis）：入队 → 查询 → 清理；未启用时不产生 job。
- 文档：新增 `docs/23-后台任务与队列.md`；`docs/12` 环境变量与启动方式、`docs/02` JobTrigger、`docs/05` §7.6.11、`docs/INDEX`。

## 非目标

- 替换所有通知为 Outbox（COM-01 后续）。
- 队列优先级、限流、重复任务调度器（cron 仍由 Web 触发）。
- 多队列拆分（邮件/报表）与独立 Worker 池。
- Prometheus 队列指标（OPS-09）。

## 风险

- 新增生产依赖 `bullmq`；已确认 `npm audit --omit=dev` 为 0 漏洞。
- 多实例 Web 同时 cron 入队：jobId 幂等去重，最终仍由咨询锁保证只执行一次。
- Worker 与 Web 必须使用同一 `QUEUE_PREFIX` 与 Redis DB，否则「入队了没人消费」。
- 失败任务默认保留会占 Redis 内存；运维需按 `GET /jobs/failed` 清理。
