# T263：合同状态机与续签修复（FIN-01）

## 背景

FIN-01 的核心缺陷：`renew()` 在原合同仍为 ACTIVE 时，为同一房间新建 DRAFT，直接撞上
`idx_contracts_room_id_unfinished`（`roomId WHERE status IN ('DRAFT','ACTIVE')`）唯一索引 →
续签在真实数据库必失败（P2002 / 500）。

同时：
- 激活「旧 ACTIVE + 新 DRAFT」时，应用层把任何未结束合同都判为冲突，续签无法收口；
- 定时任务 `autoTransitionContracts` 直接激活所有 DRAFT，续签窗口内可能产生两份 ACTIVE；
- 续签日期未校验不重叠（新合同可早于旧合同到期日）。

## 范围

### 1. 唯一约束调整

- 迁移 `20261024190000_contract_active_unique`：
  - 删除 `idx_contracts_room_id_unfinished`；
  - 新建 `idx_contracts_room_id_active`（`roomId WHERE status='ACTIVE'`）。
- 应用层继续阻止同房间重复 DRAFT/ACTIVE（`create()`），并新增续签场景的 DRAFT 互斥。

### 2. 续签（`renew`）

- 只允许 ACTIVE / EXPIRED 合同续签；DRAFT、TERMINATED、RENEWED 拒绝。
- 新合同起始日必须**晚于**原合同到期日；未提供时默认「到期日次日」。
- 新合同为 DRAFT，`renewedFromId` 指向原合同；原合同保持 ACTIVE。
- 同一合同重复续签 409（`renewedTo` + `renewedFromId @unique`）。
- 同房间已有其他 DRAFT 时拒绝续签，避免多份草稿。

### 3. 激活（`update` → ACTIVE）

- 若唯一未结束合同是「本次续签的原合同且为 ACTIVE」：
  - 校验新起始日 > 旧到期日；
  - 同一事务内先把旧合同置为 `RENEWED`，再激活新合同；
  - 房间保持 OCCUPIED（`DRAFT->ACTIVE` 的房态随动仅在 RESERVED 时生效）。
- 其他未结束合同仍 409。

### 4. 定时任务

- `autoTransitionContracts` 激活 DRAFT 时：
  - 若为续签 DRAFT，先在同一事务内把旧 ACTIVE 置为 RENEWED；
  - 仍有其他 ACTIVE 时跳过，不产生两份 ACTIVE；
  - 日期重叠时跳过并留给人工处理。

### 5. 测试

- 单元：续签创建/日期校验/重复续签；激活续签合同；定时任务先 RENEWED 后 ACTIVE。
- 集成（J6）：真实 DB 下续签不再 409；激活后旧 RENEWED、新 ACTIVE、房间 OCCUPIED。

## 风险

- 唯一索引从「DRAFT/ACTIVE」收窄为「ACTIVE」：若有人绕过 API 直接写库，可能产生多个 DRAFT；应用层与续签校验已覆盖。
- 迁移要求库中不存在同房间多份 ACTIVE；上线前先跑重复检查脚本。
- 续签窗口内旧合同仍 ACTIVE，账单仍归属旧合同；新合同账单从新起始日开始，依赖 FIN-02 的计费窗口。
- 定时任务跳过日期重叠的续签 DRAFT 时只返回较少 activated，不告警；后续 OPS-04 可加指标。
