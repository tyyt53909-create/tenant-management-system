# T288：依赖注入清理与大服务拆分（QLT-02）

## 背景

ISS-38：42 处 `@Optional()`，其中 19 处伴随 `?? new X()`。容器漏注册时不会报错，而是现场 new
一个「没有 Redis / 没有时钟 / 没有支付通道」的实例继续跑，把装配错误推迟成运行时诡异现象：

- `OTP_STORE` 缺省 → 多实例验证码不共享；
- `PAYMENT_PROVIDER` 从未被任何模块注册 → 生产漏配就静默走线下；
- `BusinessClock` 缺省 → 绕过 `BUSINESS_TIMEZONE`，月末结算可能落到错误业务日；
- `METER_ADAPTER` 缺省 → 模拟器/设备模式失效。

同时 `rooms.service.ts` 603 行混着照片规则、状态机与 CRUD。

## 范围

- **依赖必填**：bills（4 依赖 + `PAYMENT_PROVIDER` 显式注册）、meters（8 处）、auth（`OTP_STORE`、
  `LOGIN_ATTEMPT_STORE`、`FederatedAuthService`）、notifications（dispatcher）、announcements（notifications）、
  public-utilities（priceService）。
- **保留可选**：scheduler 的观测/队列开关、notifications 的 WS 网关、jwt 的 `REFRESH_STORE`、
  capability guard 的能力服务、simulator 的 anomalyRunner（清单化并注明原因）。
- **拆分 RoomsService**：`room-photos.ts`（照片 key/上限/资产绑定）、`room-transitions.ts`
  （流转表 + 前置条件），service 603 → 540 行。
- **防回归**：`dependency-hygiene.spec.ts` 静态扫描 + 双白名单 + 关键模块硬约束。
- **测试装配助手**：`meters/meter-test.providers.ts`。
- 文档 `docs/33-依赖注入与大服务拆分.md`，同步 INDEX。

## 非目标

- 拆分 `AuthService` / `TenantsService` 的业务方法本身（需先补集成用例）。
- `MetersService` 门面按领域再拆（会改动 controller 与多个 spec）。
- 引入 DI 容器外的服务定位器或全局容器。

## 验收

|---|---|---|
| 1 | 关键模块不再有 `@Optional()` 与 `?? new X()` | `dependency-hygiene.spec.ts` |

## 风险

- 依赖必填后，新增测试必须显式提供替身；漏提供会在编译期/启动期失败（这是预期摩擦）。
- 白名单需要人工维护，新增可选依赖要同步改测试。
- 拆分只覆盖 RoomsService；其它大服务留待后续，避免一次改动过大。
